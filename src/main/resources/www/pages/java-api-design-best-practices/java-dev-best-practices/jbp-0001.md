A BOM is a *Bill of Materials* that in the Java ecosystem is typically represented as a specialized Maven POM file. It includes details of many libraries, including a specific version number for each. When a project decides to include a BOM dependency, the project is relieved of the requirement of specifying a dependency version for any library that is specified within the BOM file. In fact, it is encouraged that when a BOM dependency is taken, any explicit dependency versions specified in your project's configuration file (be it a Maven `pom.xml`, a Gradle `build.gradle`, or something else) be removed, so that version decisions are left up to the BOM.

It is really important to note that including a BOM dependency does not imply that all of the dependencies listed within the BOM are automatically dependencies of the project depending on the BOM. In fact, including a BOM dependency results in zero immediate changes to your project, except that there is a new place to look for dependency versions when a dependency is specified without any versions.

Many popular projects have BOMs that developers can choose to use. For example, you can see details of BOMs for some popular projects below:

- [Azure SDK BOM](https://github.com/Azure/azure-sdk-for-java/tree/main/sdk/boms/azure-sdk-bom)
- [Jackson BOM](https://central.sonatype.com/artifact/com.fasterxml.jackson/jackson-bom)
- [JUnit BOM](https://central.sonatype.com/artifact/org.junit/junit-bom)
- [Micronaut Platform BOM](https://central.sonatype.com/artifact/io.micronaut.platform/micronaut-platform)
- [Netty BOM](https://central.sonatype.com/artifact/io.netty/netty-bom)
- [Spring Boot Dependencies BOM](https://central.sonatype.com/artifact/org.springframework.boot/spring-boot-dependencies)
- [Quarkus BOM](https://central.sonatype.com/artifact/io.quarkus.platform/quarkus-bom)

## The benefits of BOMs

The immediate question to ask is: why use BOMs? The answer is simply that the people publishing a BOM have likely taken some amount of effort to ensure that the dependencies listed within the BOM work together. For example, in the Azure SDK for Java, the dependencies listed in the BOM are tested (and proven through rigorous tooling) to ensure that the transitive closure of all dependencies is as minimal as possible (which is just a fancy way of saying we really try our hardest to avoid dependency conflicts for you).

Once you move to using a BOM, your burden of [keeping dependencies up to date](/jbp/jbp-4.html) is lessened due to the fact that you have far fewer dependencies whose version is explicitly expressed. Now, your burden is to upgrade BOM versions at times that are appropriate for you.

## How to use a BOM

### Maven

In Maven, a BOM is included within the `dependencyManagement` section of a Maven POM file, rather than the standard `dependency` section for normal dependencies. For example, including the [Azure SDK BOM](https://github.com/Azure/azure-sdk-for-java/tree/main/sdk/boms/azure-sdk-bom) would be achieved as shown below (be sure to [check Maven Central for the latest version](https://central.sonatype.com/artifact/com.azure/azure-sdk-bom)):

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.azure</groupId>
      <artifactId>azure-sdk-bom</artifactId>
      <version>1.3.10</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

Once a BOM has been specified (and note, you can include more than one BOM in a project), you can remove the version numbers from any dependency listed in the BOM. For example, a dependency on `azure-storage-blob` should appear as the following:

```xml
<dependencies>
  <dependency>
    <groupId>com.azure</groupId>
    <artifactId>azure-storage-blob</artifactId>
  </dependency>
</dependencies>
```

You can read more about importing BOMs in a Maven project in the [Maven documentation](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html#bill-of-materials-bom-poms).

### Gradle

Gradle provides support for importing Maven BOM files, but unlike in Maven, Gradle BOMs are included via a regular dependency declaration on the BOM, wrapped in `platform(...)`. For example, using the Gradle Kotlin DSL (`build.gradle.kts`):

```kotlin
dependencies {
    // import a BOM
    implementation(platform("com.azure:azure-sdk-bom:1.3.10"))

    // define dependencies without versions
    implementation("com.azure:azure-storage-blob")
}
```

If your Gradle project uses a [version catalog](https://docs.gradle.org/current/userguide/version_catalogs.html) (`gradle/libs.versions.toml`), the BOM is the only entry that needs a version, and the libraries it manages can be declared without one:

```toml
[versions]
azure-bom = "1.3.10"

[libraries]
azure-bom = { module = "com.azure:azure-sdk-bom", version.ref = "azure-bom" }
azure-storage-blob = { module = "com.azure:azure-storage-blob" }
```

```kotlin
dependencies {
    implementation(platform(libs.azure.bom))
    implementation(libs.azure.storage.blob)
}
```

You can read more about importing BOMs in a Gradle project in the [Gradle documentation](https://docs.gradle.org/current/userguide/platforms.html#sub:bom_import).

## When a BOM and a dependency disagree

It is worth understanding what happens when a version is specified in more than one place. In Maven, an explicit `<version>` on a dependency always wins over a version from an imported BOM, and when two imported BOMs manage the same artifact, the one declared *first* wins. In Gradle, platforms participate in conflict resolution, so the highest requested version typically wins unless you use `enforcedPlatform(...)`. In both cases, the lesson is the same: once you have adopted a BOM, resist the temptation to override versions it manages unless you have a specific, documented reason (for example, picking up an urgent security fix before the next BOM release).

## Upgrading a BOM

Remember that upgrading a BOM upgrades every library it manages in a single step. Well-run BOMs increment their major version whenever any listed library has a breaking change (see [publish BOMs for multi-module projects](/jbp/jlbp-4.html)), so treat a BOM major version upgrade as a breaking change: read the release notes to find out which libraries changed major version, and follow their migration guides. If you need to stay on an older major version of one library for a while, you can temporarily override its version, but make sure that override is tracked and removed. After any BOM upgrade, check that your dependency graph still converges (for example, with the Maven Enforcer plugin's `dependencyConvergence` rule), as described in [avoid diamond dependency conflicts](/jbp/jlbp-21.html).
