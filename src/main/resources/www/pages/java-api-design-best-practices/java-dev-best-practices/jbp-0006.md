The Java ecosystem has created a lot of very useful build tools, the most popular being Maven and Gradle. Projects using these build tools are fortunate to have a good number of plugins that enable static code analysis and other kinds of project validation. These plugins can provide great insights into issues with your project, so it is worthwhile spending time enabling these plugins and ensuring that they are configured properly.

## Compiler warnings

The cheapest static analysis tool of all is the Java compiler itself. Enabling `-Xlint:all` (and, once the codebase is clean, `-Werror`) surfaces deprecation usage, unchecked generic operations, missing `serialVersionUID` values, and many other issues for free. Similarly, enabling Javadoc's doclint checks (covered in [write great documentation](/jbp/jlbp-11.html)) keeps documentation honest.

## Dependency checking

We've already spoken about using the Maven Dependency and Versions plugins for Maven in the [keep our dependencies up to date](/jbp/jbp-4.html) best practice. It is also worth configuring the [Maven Enforcer Plugin](https://maven.apache.org/enforcer/maven-enforcer-plugin/), which can fail the build when rules are broken. Particularly useful rules include `requireUpperBoundDeps` and `dependencyConvergence` (which detect the diamond dependency conflicts discussed in [minimize dependencies](/jbp/jbp-2.html)), `requireMavenVersion` / `requireJavaVersion`, and `banDuplicatePomDependencyVersions`. Gradle users can achieve similar results with [dependency resolution strategies](https://docs.gradle.org/current/userguide/resolution_strategy_tuning.html) such as `failOnVersionConflict()`.

## SpotBugs

[SpotBugs](https://spotbugs.github.io/) is a great tool for finding bugs in code through static analysis. It integrates well into Maven and Gradle and can generate extremely useful reports about the quality of a codebase.

The SpotBugs project publishes short documents that detail how to integrate SpotBugs [into Maven](https://spotbugs.readthedocs.io/en/latest/maven.html) and [into Gradle](https://spotbugs.readthedocs.io/en/latest/gradle.html). Once integrated into the build process for your project, the next step is calling the appropriate build targets to generate a human-readable HTML report. Working through the reported issues will be a good learning experience for every developer about things they need to consider when coding, but it may be the case that sometimes SpotBugs will report false positives. Fortunately, these can be suppressed if they are truly incorrect, so that they do not prevent us from being 'SpotBugs-clean'.

A good goal for SpotBugs in any project is to get the codebase entirely clean of any reported issues, and once that is achieved, enable the build to fail if a SpotBugs issue is encountered. This provides protection against the code base getting worse with known issues.

## Error Prone and NullAway

[Error Prone](https://errorprone.info/) takes a different approach to SpotBugs: rather than analyzing compiled bytecode after the fact, it runs as a plugin *inside* the Java compiler, so bug patterns are reported as compiler errors and warnings in the same place developers are already looking. It catches a wide range of common mistakes, and many of its checks offer suggested fixes.

Error Prone also serves as the host for [NullAway](https://github.com/uber/NullAway), a fast nullness checker. When combined with [JSpecify](https://jspecify.dev/) annotations, NullAway can eliminate most `NullPointerException`s at compile time. This is covered in more detail in the [make nullness explicit](/jbp/jlbp-18.html) best practice.

## Formatting

Arguments over code formatting in code review are a waste of everyone's time. Rather than relying on a style checker to *complain* about formatting, consider a tool that *fixes* it automatically, such as [Spotless](https://github.com/diffplug/spotless) (for Maven and Gradle) configured with a formatter like [google-java-format](https://github.com/google/google-java-format) or [Palantir Java Format](https://github.com/palantir/palantir-java-format). Run it automatically on every build (or as a pre-commit hook), and enforce it in CI with the `check` goal.

## CheckStyle

[CheckStyle](https://checkstyle.sourceforge.io/) is a vastly less critical tool than SpotBugs, but it is useful in enforcing some degree of consistency of code style (and with a formatter handling whitespace and layout, CheckStyle can focus on the rules that actually matter). It is also extensible: in the Azure SDK for Java we wrote custom CheckStyle rules to enforce our API design guidelines, such as preventing types in `implementation` packages from leaking into public API. It again plugs into Maven and Gradle build processes and can automatically warn via report or via build failures when the code style is no longer being adhered to. It is important to configure CheckStyle with the rules that are critical to your team, and to not just throw all available rules at it. This is because no one has fun fixing failing builds because there is a missing space between the `if` statement and its opening bracket, and other mostly-useless rules. It is best practice to sit the development team down together and pick out the rules that they all agree are useful, and enable only those.

## JaCoCo

[JaCoCo](https://www.jacoco.org/jacoco/) is a code-coverage tool that can visually display the amount of code that is tested by your unit tests. It helps you to identify where test coverage may be lacking, and can be used, in conjunction with Maven, to enforce a minimum level of coverage at all times.

! We should not be so data-driven that we write tests purely for the sake of satisfying JaCoCo! Our goals in writing unit tests should always be to ensure correctness of our implementation, and to protect against the accidental introduction of bugs.

## API compatibility checking

For library developers, one of the most valuable build plugins is one that detects breaking API changes before they are released. Tools such as [japicmp](https://siom79.github.io/japicmp/) and [Revapi](https://revapi.org/) compare the API of the code being built against the most recently released version, and can fail the build when an incompatible change is detected. This is covered in more detail in the [resist breaking changes](/jbp/jlbp-6.html) best practice.
