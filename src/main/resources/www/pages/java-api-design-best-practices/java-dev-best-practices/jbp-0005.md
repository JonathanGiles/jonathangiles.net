Having a good logging story in all Java applications can be a real lifesaver when something goes wrong. The challenge is learning what to log and how to use the logging frameworks to their full potential to spread log output across the numerous logging levels (e.g. trace, debug, info, warn, error), as well as to not impact the performance of the application with all the extra logging code.

Java has a plethora of logging frameworks, so it can often be confusing how to get started, but it is important to make a start so as to not be caught flat-footed when logging could have been useful.

## Choosing a logging framework

As noted in the best practice on [minimizing dependencies](/jbp/jbp-2.html), sometimes the decision about which dependency we should use is made for us by the fact that one of our dependencies has a dependency (directly or transitively) on a particular type of framework, and this is especially the case with logging frameworks! If we already find a logging framework on our dependency classpath, we should try our best to use it.

It's a good idea to not depend on a specific logging implementation whenever possible, and instead write our code against a logging *facade*. This means we do not need to directly concern ourselves with which particular logging implementation is used at runtime, and that gives us (and, for library developers, our users) the flexibility to choose the most appropriate implementation.

The two facades worth considering today are:

* **[SLF4J](https://www.slf4j.org/)** is the de facto standard logging facade in the Java ecosystem. Version 2.x (which requires Java 8 or later) adds a fluent API, supplier-based lazy arguments, and key-value pairs for structured logging. Most applications will already have SLF4J on their classpath, so it is usually the pragmatic choice.
* **[`System.Logger`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.Logger.html)** is the platform logging API that shipped in Java 9. Because it is part of the JDK, it adds no dependencies, which makes it attractive to library developers who want to [minimize dependencies](/jbp/jbp-2.html). By default it routes to `java.util.logging`, but bridges exist to route it to SLF4J, Log4j 2, and others.

Application developers then choose a logging *implementation*, such as [Logback](https://logback.qos.ch/) or [Log4j 2](https://logging.apache.org/log4j/2.x/), and configure the facades to route to it.

! Library developers should never ship a logging implementation (or its configuration file) as a compile or runtime dependency. Doing so takes the choice away from the application developer and frequently results in duplicate bindings, warnings at startup, or log output disappearing entirely.

## Understanding logging levels

The value in logging is the ability to look back after an event and discern why that event happened. Often we can find ourselves underwhelmed or overwhelmed by our log output, with not enough useful data to determine the issue, or with so much information it is impossible to find the needle within the haystack. Logging frameworks all have the concept of logging levels, and it is critical to understand how to put these to best use. 

SLF4J, for example, offers `TRACE`, `DEBUG`, `INFO`, `WARN`, and `ERROR` levels. A summary of each of these levels is below:

* **TRACE:** The most fine-grained level and therefore extremely verbose. At this level it is ok to log each step of an algorithm or each query going to a web service.
* **DEBUG:** Not as fine-grained as `TRACE`, but this level should be used to log information needed to diagnose issues that does not ordinarily need to be presented to viewers of the log output.
* **INFO:** This is typically the default logging level, and should be used when something expected but noteworthy happens, such as a service starting up or a significant state transition. `INFO` output should be concise enough that it is reasonable to leave it enabled in production.
* **WARN:** This log level is for when something unexpected has happened that may have been recovered from or is non-critical.
* **ERROR:** This log level is used to indicate that some functionality has failed to perform some critical function.

If all we did was log everything in the `INFO` level, we are making the lives of future log file reviewers much harder. It is important that we spread our logging out over all available levels, and critically, we make use of the `TRACE` and `DEBUG` levels appropriately, so that we do not become 'top-heavy', with most of our logging only going into `INFO`, `WARN`, and `ERROR`.

Library developers in particular should be restrained at the `INFO` level and above. A library that logs at `INFO` on every operation quickly becomes a library that users configure to be silent - and then the valuable `WARN` and `ERROR` messages are lost too.

## What not to log

Logs are frequently shipped to centralized systems, retained for long periods, and read by many people. Never log secrets (passwords, API keys, access tokens, connection strings), and be careful about logging personal data or entire request and response payloads. Where it is necessary to log a request for diagnostics, redact sensitive headers and fields first.

It is also worth remembering that log messages can become an unintentional contract. As noted in the [characteristics of good API](/jbp/jlbp-1.html), users will parse your log output, so treat changes to important log messages with some care.

## Logging performance considerations

There are so many ways to have great intentions with logging and then fail when it comes time to implement it. Normally the failure relates to a performance hit that is taken when logging is included. I have over many years observed many such logging failures, such as the ones noted below:

1. **Eager concatenation of objects when logging may not even occur.** For example:

    ```java
    // Example 1: Critical performance code path
    public void criticalPath(CoreStrategy strategy) {
      // BAD! Performing toString() on CoreStrategy example class may be slow
      LOGGER.debug("Entering critical code path with strategy " + strategy);
    }
    ```

    There is the likelihood that calling `strategy.toString()` may be an expensive and slow operation, but it is called regardless of the logging level, which means we pay the price every time. Additionally, we are also performing string concatenation, again potentially without need. A better approach is to use parameterized messages, passing the argument to the logger and having it only perform the formatting if the log level is enabled. For example:

    ```java
    // Example 2: Critical performance code path
    public void criticalPath(CoreStrategy strategy) {
      // GOOD! Not eagerly implicitly calling toString on strategy
      LOGGER.debug("Entering critical code path with strategy {}", strategy);
    }
    ```

    SLF4J has overloads for each logging level with the following forms:

    ```java
    debug(String msg)
    debug(String format, Object arg)
    debug(String format, Object arg1, Object arg2)
    debug(String format, Object... args)
    ```

    We can put as many `{}` placeholders into our strings as we have arguments, but only the one-arg and two-arg calls will be of the very fastest form. For more than two args, there is the implicit creation of an `Object[]` to contain all the args. Whilst this is a non-free cost, it is negligible and should not be of major concern in most cases.

    Whilst this may seem all very academic, the [SLF4J FAQ](https://www.slf4j.org/faq.html#logging_performance) notes that the parameterized form is dramatically faster than string concatenation when the log level is disabled. I would recommend not wasting CPU cycles needlessly!

2. **Lack of familiarity with Supplier-based APIs.** Parameterized messages avoid the cost of formatting, but they don't help when computing the *argument itself* is expensive. Modern logging APIs accept a `java.util.function.Supplier`, which defers the computation until (and only if) the log statement is actually going to be emitted. For example, using the SLF4J 2.x fluent API:

    ```java
    // Example 3: Slow logging computation deferred until (and only if) required
    public void criticalPath(CoreStrategy strategy) {
      // GOOD! computeComplexLoggingOutput() is only called if DEBUG is enabled
      LOGGER.atDebug()
            .setMessage("Entering critical code path with strategy {}")
            .addArgument(() -> computeComplexLoggingOutput(strategy))
            .log();
    }
    ```

    The equivalent using the JDK's `System.Logger` is:

    ```java
    LOGGER.log(System.Logger.Level.DEBUG,
               () -> "Entering critical code path with strategy " + computeComplexLoggingOutput(strategy));
    ```

    The benefit of this approach is that the expensive method is only called if the logging framework deems the output necessary. It avoids the eagerness of the code examples in the first tip above.

3. **Guard clauses where they are no longer needed.** Before parameterized and supplier-based APIs existed, the standard advice was to wrap log statements in `if (LOGGER.isDebugEnabled()) { ... }`. This is still occasionally useful when a whole block of code exists purely to produce log output, but in most cases the approaches above are cleaner and just as fast.

## Structured logging

When logs are consumed by machines (as they almost always are in cloud environments), it is far more useful to emit structured data than to bury values inside a sentence. SLF4J 2.x supports key-value pairs that compatible backends can output as separate fields (for example, as JSON):

```java
LOGGER.atInfo()
      .setMessage("Order processed")
      .addKeyValue("orderId", order.id())
      .addKeyValue("durationMs", elapsed.toMillis())
      .log();
```

Combined with the [OpenTelemetry](https://opentelemetry.io/docs/languages/java/) integrations available for most logging backends, this makes it far easier to search, aggregate, and correlate log output with traces and metrics. Library developers should also see [instrument with OpenTelemetry](/jbp/jlbp-25.html).
