Java releases are made every six months in a 'feature-release-train' model, rather than having a major release planned for every two to four years as historically was the case. Within this cadence, Oracle and other participants in the Java ecosystem designate certain releases as *Long-Term Support* (or LTS) releases. LTS releases were originally every three years (Java 11 in September 2018 and Java 17 in September 2021), but since Java 17 the cadence has been every two years. The recent LTS releases are therefore Java 17 (September 2021), Java 21 (September 2023), and Java 25 (September 2025), with the next LTS expected to be Java 29 in September 2027.

The major difference between non-LTS releases and LTS releases is that when a new release is made available (every six months), the previous non-LTS release is out of support. When a release leaves support, it means that it won't receive quarterly security, stability, or performance updates any longer. LTS releases, on the other hand, continue to receive updates from many vendors for many years. Most organizations still prefer to target LTS versions for production use because it is not always possible to test and update their production JDK every six months.

Non‑LTS releases are a cumulative set of enhancements on top of the most recent LTS release. These are good releases to test with so that you can have higher degrees of confidence that moving to the next LTS will be straightforward, but you should avoid using non-LTS releases in production unless you can test and update the JDK with every new release.

! The guidance in this best practice is about the JDK you *run* your applications on. Library developers have a different, related decision to make about the *minimum* Java version their library supports - see [choose your Java baseline deliberately](/jbp/jlbp-20.html).

## Why upgrade?

It can be tempting to stay on an older LTS release for as long as a vendor will support it. However, each LTS release brings a substantial set of improvements that you are missing out on, often with no code changes required. Since Java 11, for example, we have gained:

* **Language features** that make code more concise and safer, including `var` (Java 10), switch expressions (Java 14), text blocks (Java 15), records (Java 16), pattern matching for `instanceof` (Java 16), sealed classes (Java 17), record patterns and pattern matching for `switch` (Java 21), unnamed variables (Java 22), and module import declarations, flexible constructor bodies, and compact source files (Java 25).
* **Virtual threads** (Java 21), which allow simple, blocking, thread-per-request code to scale to very high levels of concurrency.
* **Performance and footprint improvements** across the JIT compilers, garbage collectors (including generational ZGC and Shenandoah), and startup (such as the AOT cache work from Project Leyden, starting in Java 24).
* **New APIs**, such as sequenced collections (Java 21), the Foreign Function & Memory API (Java 22), and stream gatherers (Java 24).

Very often, simply moving an existing application to a newer JDK - without changing a line of code - results in measurable improvements in throughput, latency, and memory usage.

## Keeping the JDK up to date

The OpenJDK project releases quarterly patch updates in January, April, July, and October. These patch updates contain fixes to security vulnerabilities and critical bug fixes, as well as additional non-security bug fixes.

The main recommendation is to keep JDK installs up to date with all patch updates to ensure the latest security vulnerability fixes and other improvements are available. For example, if you use Java 21 and the JDK version used in production is still 21.0.1, then you are missing years of important security, stability, and performance fixes, defeating the purpose of LTS releases. As patch updates within the same major version are generally backward compatible, they provide a low-risk vehicle for the potentially urgent deployment of security fixes. If you deploy using container images, make sure your base images are rebuilt and redeployed regularly, so that they pick up these patch updates.

## Which build of Java should I use?

Java releases used to be simple - you'd download a build for a particular operating system from the Sun Microsystems website, and that was it. Today, because the OpenJDK is open source, numerous companies make available builds of the OpenJDK that are functionally equivalent (they all pass the Java SE compatibility tests). Some companies also offer enhanced builds of OpenJDK that offer improved performance, security, or other enhancements.

If your needs are simple and you do not require any form of commercial support, any build of OpenJDK that receives regular updates will be sufficient. Some distributions include:

* [Eclipse Temurin](https://adoptium.net) (formerly AdoptOpenJDK)
* [Microsoft Build of OpenJDK](https://www.microsoft.com/openjdk)
* [Azul Zulu](https://www.azul.com/downloads/?package=jdk)
* [BellSoft Liberica JDK](https://bell-sw.com/pages/downloads/)
* [Amazon Corretto](https://aws.amazon.com/corretto/)
* [SapMachine](https://sap.github.io/SapMachine/)
* [Oracle JDK](https://www.oracle.com/java/technologies/downloads/)

A commonly recommended choice is [Eclipse Temurin](https://adoptium.net), but in general you should choose the vendor that most closely matches your environment or needs. Check how long each vendor commits to supporting each LTS release, as this varies. Also be aware that the OpenJDK builds published at [jdk.java.net](https://jdk.java.net) only receive updates for six months, until the next feature release, and so are not a good choice if you are targeting an LTS release in production.

If you are looking for a supported offering, a good choice is to choose a build from your cloud provider, such as the [Microsoft Build of OpenJDK](https://www.microsoft.com/openjdk) if you are using Azure, as these will offer the best integration and support options for you and your cloud of choice.

Tools such as [SDKMAN!](https://sdkman.io/) make it easy to install and switch between multiple JDK distributions and versions on a development machine, and the [Maven Toolchains](https://maven.apache.org/guides/mini/guide-using-toolchains.html) and [Gradle Toolchains](https://docs.gradle.org/current/userguide/toolchains.html) features let a build declare the JDK version it requires, independently of the JDK used to run the build tool itself.

## Don't let dependencies hold you back

Oftentimes the reason a Java version choice is made is because of a dependency of our project having a hard dependency on a particular version of Java. Historically this was a significant problem with the move beyond Java 8, as the introduction of modules and the strong encapsulation of JDK internals (fully enforced since Java 17) broke libraries that relied on those internals. Today the situation is reversed: the vast majority of the ecosystem supports recent LTS releases, and major frameworks now *require* them (for example, Spring Boot 3 and later, and Jakarta EE 11, require at least Java 17).

It is beneficial every release cycle, when we are looking at [updating our dependencies](/jbp/jbp-4.html), to identify which, if any, of our dependencies still force us back to earlier versions of Java, and to ask questions:

* Do I still need this dependency?
* Is there a suitable replacement for this dependency?
* Is this dependency still being actively developed?
* Why hasn't this dependency moved forward?
* Can I help to unblock this dependency, with code, bug reports, or reproducible test cases?

Because our goal is to always go to production with the latest Java LTS release, we need to be increasingly clear in our own minds on what we need to do to be at that point. If the likelihood of one of our dependencies never unblocking us is too high, we should find another path if at all possible. Falling off the LTS support window is undesirable and will grow to become more of a technical debt the longer we wait to resolve it.

A good habit is to run your CI build against the latest non-LTS release (and even early-access builds of the next release) in addition to your production LTS. This surfaces incompatibilities months before you need to upgrade, while there is still time to report them to the relevant projects.
