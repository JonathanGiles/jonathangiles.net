The Java ecosystem is great for its breadth and depth of libraries. Their availability helps to fill in gaps in the JDK, and they make us all much more productive. The problem with dependencies is the fact that everyone's development style and philosophy around breaking changes, versioning, dependency management, and so on is all so varied, and we import these different approaches into our projects when we include a dependency. We have to be sure that each dependency pays for the cost of including it.

## What is the cost of a dependency?

When a dependency is included in a project, we have to assume that the dependency will be included in the project forever. The biggest concerns that we must have with bringing in dependencies are:

1. Each dependency brings with it the potential for security vulnerabilities (as the industry learned painfully with [Log4Shell](https://en.wikipedia.org/wiki/Log4Shell) in late 2021), and expands the [software supply chain](/jbp/jbp-9.html) that you need to keep secure.
2. Each dependency typically has other dependencies, forming a transitive dependency chain.
3. Transitive dependencies from different direct dependencies may conflict with each other, resulting in runtime exceptions.
4. Correctness of the functionality offered by the dependency.
5. Support/maintenance offered by the developers of the dependency.

## Don't duplicate functionality

Because there are so many libraries out in the Java ecosystem, we will often find ourselves with dependencies on multiple libraries that provide essentially the same functionality, for example Jackson and Gson for JSON processing. Often the choice of which library should be used directly by our project is already made for us by being a transitive dependency of another dependency. For example, Spring is tightly bound to Jackson for its JSON processing needs, and it would seem unwise in this case to use anything other than Jackson for our JSON processing needs.

It is also worth checking whether the JDK itself now provides what we need. Many dependencies that were near-universal in 2015 are much less necessary today. For example, `java.net.http.HttpClient` (Java 11) covers most HTTP client needs, `java.time` replaced Joda-Time, `List.of(...)` / `Map.of(...)` and friends cover much of what we once used Guava for, and records (Java 16) remove much of the motivation for code-generation libraries such as Lombok for simple data carriers.

## Understanding dependencies

Fortunately build tools such as Maven and Gradle give us useful tools to understand our dependencies (including all transitive dependencies). Developers should frequently run the following commands on their project, particularly when a dependency is added or [upgraded to a newer version](/jbp/jbp-4.html):

* For **Maven**, run `mvn dependency:tree`
* For **Gradle**, run `./gradlew dependencies`

When these tools are run, we should always try to justify each dependency, and the justification required should be amplified by the number of transitive dependencies it brings with it - the more there are, the stronger the justification should be for the dependency to be included. Maven's `mvn dependency:analyze` goal is also useful here, as it reports dependencies that are declared but unused (candidates for removal), and dependencies that are used but undeclared (which should be declared explicitly rather than relied upon transitively).

## Dependency scope

Our project files let us define dependencies in a number of different scopes, and these scopes impact the availability of the dependency in certain conditions. In Maven there are [six dependency scopes](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html#Dependency_Scope), the most common of which are:

* **compile**: The default scope if none is specified, compile dependencies are available at build and runtime of the application.
* **test**: This scope specifies that the dependency is only available when compiling and executing tests, and will not be available when compiling or running the application itself.
* **provided**: The dependency is needed at compile time, but is expected to be supplied by the runtime environment (for example, the Jakarta Servlet API inside an application server).
* **runtime**: The dependency is not needed to compile our code, but is needed at runtime (for example, a JDBC driver or a logging implementation).

It is important to properly apply the correct scope (especially the 'test' scope) so that we do not bring more dependencies in at compile and run time than necessary. For example, a JUnit dependency should be part of the test scope, and in Maven would look as follows:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter-api</artifactId>
    <scope>test</scope>
</dependency>
```

Note that in the example above, no version is specified, as it is expected that you would [use the JUnit BOM](/jbp/jbp-1.html).

Gradle has a similar concept, which it calls *configurations*. The most important distinction for library developers is between `api` (the dependency is part of our public API and is exposed to consumers at compile time) and `implementation` (the dependency is an internal detail and does not leak onto our consumers' compile classpath). Preferring `implementation` wherever possible is one of the easiest ways to reduce the burden we place on our users. The equivalent JUnit dependency in Gradle (Kotlin DSL), again using the JUnit BOM, would be the following:

```kotlin
testImplementation(platform("org.junit:junit-bom:6.1.3"))
testImplementation("org.junit.jupiter:junit-jupiter")
```
