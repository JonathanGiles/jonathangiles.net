Every dependency we add, every build plugin we configure, and every repository we download artifacts from becomes part of our *software supply chain*. In December 2021, [Log4Shell](https://en.wikipedia.org/wiki/Log4Shell) demonstrated just how exposed the Java ecosystem is to this: a single vulnerability in a ubiquitous logging library affected a huge proportion of Java applications, and many organizations spent weeks simply trying to work out *whether* they were affected, because they had no reliable inventory of what was inside their applications.

Many of the other best practices on this site - [minimizing dependencies](/jbp/jbp-2.html), [not floating dependency versions](/jbp/jbp-3.html), and [keeping dependencies up to date](/jbp/jbp-4.html) - are, in part, supply chain practices. This best practice covers the remaining pieces.

## Know what you ship: generate an SBOM

A *Software Bill of Materials* (SBOM) is a machine-readable inventory of every component in a piece of software, including all transitive dependencies and their versions. (Not to be confused with the Maven [BOM](/jbp/jbp-1.html), which manages versions rather than describing what was shipped.) With an SBOM generated for every build, answering the question "are we affected by this new vulnerability?" becomes a query rather than an investigation.

The two dominant SBOM formats are [CycloneDX](https://cyclonedx.org/) and [SPDX](https://spdx.dev/), and both have good tooling for Java. For example, the [CycloneDX Maven Plugin](https://github.com/CycloneDX/cyclonedx-maven-plugin) can generate an SBOM as part of every build:

```xml
<plugin>
  <groupId>org.cyclonedx</groupId>
  <artifactId>cyclonedx-maven-plugin</artifactId>
  <version>2.9.3</version>
  <executions>
    <execution>
      <phase>package</phase>
      <goals>
        <goal>makeAggregateBom</goal>
      </goals>
    </execution>
  </executions>
</plugin>
```

An equivalent [CycloneDX Gradle Plugin](https://github.com/CycloneDX/cyclonedx-gradle-plugin) exists for Gradle users. Library developers can also publish their SBOM to Maven Central alongside their artifacts, which helps downstream consumers build a complete picture.

## Scan for known vulnerabilities

Once you know what you ship, you can continuously check it against databases of known vulnerabilities. Options include:

* [GitHub Dependabot alerts](https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts) and [dependency review](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-dependency-review), which flag vulnerable dependencies in your repository and in incoming pull requests.
* [OWASP Dependency-Check](https://owasp.org/www-project-dependency-check/), which has Maven and Gradle plugins and can fail the build above a configurable severity threshold.
* [OSV-Scanner](https://google.github.io/osv-scanner/), which checks lock files and SBOMs against the open-source [OSV](https://osv.dev/) database.
* Commercial offerings such as Snyk, Sonatype, and others.

Vulnerability scanners inevitably produce some false positives (for example, a vulnerability in a part of a library that you don't use). Rather than ignoring the scanner entirely, record and justify each suppression, so that it is revisited when circumstances change.

## Control where artifacts come from

* **Prefer Maven Central.** As discussed in [release to Maven Central](/jbp/jlbp-3.html), Maven Central has strict requirements around namespace ownership and signing. Every additional repository you add to your build is another party you are trusting, and a potential vector for dependency confusion attacks.
* **Use a repository manager in organizations.** Proxying Maven Central through a repository manager (such as Sonatype Nexus, JFrog Artifactory, or a cloud provider's equivalent) gives you a single place to cache, audit, and block artifacts.
* **Verify what you download.** Gradle supports [dependency verification](https://docs.gradle.org/current/userguide/dependency_verification.html), which records the expected checksums (and optionally PGP signatures) of every dependency and plugin in a `verification-metadata.xml` file, and fails the build if anything changes unexpectedly. Maven users can run builds with `--strict-checksums` (`-C`) so that checksum mismatches fail the build rather than merely producing a warning.
* **Pin your build tooling too.** Commit the Maven Wrapper (`mvnw`) or Gradle Wrapper (`gradlew`) to your repository, pin plugin versions, and validate the Gradle Wrapper JAR (for example, with the [Gradle wrapper validation action](https://github.com/gradle/actions/tree/main/wrapper-validation)).

## Make builds reproducible

A build is *reproducible* if building the same source code always produces bit-for-bit identical output. Reproducible builds allow anyone to independently verify that a published binary really was built from the source it claims to be built from. Most of the work is already done for you by modern versions of Maven and Gradle; the main remaining step is to fix the timestamps recorded in archives. In Maven, this is achieved by setting a single property (which the Maven Release Plugin will update automatically):

```xml
<properties>
  <project.build.outputTimestamp>2026-01-01T00:00:00Z</project.build.outputTimestamp>
</properties>
```

In Gradle, archive tasks are reproducible by default as of Gradle 9; on earlier versions, set `isPreserveFileTimestamps = false` and `isReproducibleFileOrder = true` on archive tasks. The [Reproducible Builds for the JVM](https://reproducible-builds.org/docs/jvm/) documentation covers the details, and the `artifact:compare` goal of the Maven Artifact Plugin can verify that your build is reproducible. Library developers should also read [make your releases reproducible](/jbp/jlbp-26.html).

## Further reading

The [OpenSSF](https://openssf.org/) publishes a wealth of guidance in this area, including the [OpenSSF Scorecard](https://scorecard.dev/) (an automated assessment of the security practices of open source projects - useful both for evaluating your dependencies and for improving your own projects) and the [SLSA](https://slsa.dev/) framework for build provenance.
