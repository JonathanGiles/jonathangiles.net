title: Understand functional interfaces

In Java 8 the `@FunctionalInterface` annotation was introduced, allowing API developers to designate that a particular interface is intended for use with lambda expressions and method references. It is not necessary that an interface have this annotation, but by having this associated with an interface, it enables the compiler to enforce that the interface has exactly one abstract method, which is the requirement for supporting lambda expressions.

From a developer's point of view this is beneficial as it ensures that an interface intended for use in lambda expressions does not accidentally lose that ability with the introduction of additional abstract methods - because the compiler will not allow this situation to arise.

Having said this, developers should have some reticence to creating their own functional interfaces, as recent releases of the JDK ship with 43 functional interfaces baked in, as part of the [java.util.function](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/function/package-summary.html) package. Most of these are variations (two-argument `Bi*` forms, and primitive specializations such as `IntPredicate` or `ToLongFunction`) of six basic shapes, outlined below:

| Interface           | Signature             |
|---------------------|-----------------------|
| `UnaryOperator<T>`  | `T apply(T t)`        |
| `BinaryOperator<T>` | `T apply(T t1, T t2)` |
| `Predicate<T>`      | `boolean test(T t)`   |
| `Function<T,R>`     | `R apply(T t)`        |
| `Supplier<T>`       | `T get()`             |
| `Consumer<T>`       | `void accept(T t)`    |

Developers can choose to use these functional interfaces in lieu of creating their own, but there are still valid reasons for creating a custom functional interface. Examples include wanting a more descriptive name for the interface (for example, `Comparator` is a very expressive name for the function it serves), wanting to introduce additional functionality (such as default and static methods, as `Comparator` does with `reversed()`, `thenComparing(...)`, and `comparing(...)`), and needing a signature that the standard interfaces don't cover - most commonly, a function that throws a checked exception.

When accepting functional interfaces as parameters in our API, there are a few further considerations:

* **Prefer primitive specializations** (e.g. `IntPredicate` over `Predicate<Integer>`) to [avoid boxing](/jbp/jlbp-16.html).
* **Use wildcards for flexibility.** Accepting `Function<? super T, ? extends R>` rather than `Function<T, R>` allows users to pass a wider range of functions, as the JDK's own `Stream.map` does.
* **Beware of overloading methods that accept different functional interfaces** of the same shape in the same argument position (for example, `submit(Callable<T>)` and `submit(Runnable)`). Overload resolution with lambdas can be ambiguous, resulting in confusing compiler errors for users, or a different overload being selected than they expected. Giving such methods distinct names is usually clearer.
