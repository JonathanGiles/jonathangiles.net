Application developers should [use the latest Java LTS release](/jbp/jbp-7.html), because they control the JDK that their code runs on. Library developers have a harder decision: every library has a *minimum* supported Java version (its *baseline*), and that baseline is imposed on every application that uses the library. Choose too old a baseline, and we deny ourselves modern language features and APIs, and pay a growing maintenance cost. Choose too new a baseline, and we lock out a portion of our potential users.

## Choosing a baseline

There is no single right answer, but some considerations are:

* **Who are your users?** Look at data rather than guessing. Your own telemetry, your users' issue reports, and industry surveys of Java version usage can all help. Enterprise-focused libraries typically need to trail the latest LTS by at least one LTS release.
* **What do your dependencies and frameworks require?** If your library is primarily used with a framework that already requires a particular Java version (for example, Spring Boot 3 and later require Java 17), there is little value in supporting anything older.
* **What would a newer baseline give you?** Moving from Java 8 to Java 17 gives you modules, records, sealed classes, `var`, text blocks, switch expressions, `java.net.http.HttpClient`, and much more. Moving to Java 21 adds virtual threads, sequenced collections, and pattern matching for `switch`.
* **Track the ecosystem.** Many popular libraries have now moved to a Java 17 baseline, and Java 8 is increasingly unsupported. A reasonable default for a new library today is a Java 17 or Java 21 baseline.

Whatever baseline is chosen, document it clearly, and remember that raising it is a [breaking change](/jbp/jlbp-5.html) that should coincide with a major version increment and be clearly communicated in advance (perhaps as part of your [deprecation policy](/jbp/jlbp-14.html)).

## Compile against your baseline with `--release`

A common mistake is to build a library with a newer JDK, using `-source` and `-target` to produce bytecode for an older version. This is not enough: the compiler still compiles against the *newer* JDK's class library, so it is easy to accidentally call an API that doesn't exist on the baseline, resulting in a `NoSuchMethodError` for users at runtime. (The classic example is `ByteBuffer.flip()`, whose return type changed in Java 9, breaking libraries compiled on Java 9+ with `-target 8` when they ran on Java 8.)

The `--release` flag (Java 9 and later) solves this by compiling against the API signatures of the target release. Always use it:

```xml
<properties>
  <maven.compiler.release>17</maven.compiler.release>
</properties>
```

```kotlin
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release = 17
}
```

## Test on every version you support

A library should be tested on its baseline, on every LTS release since, and on the latest feature release. A CI matrix (for example, with GitHub Actions) makes this straightforward. It is also well worth testing against [early-access builds](https://jdk.java.net/) of the next JDK release, so that incompatibilities are found (and reported) before users find them for you. Maven and Gradle [toolchains](/jbp/jbp-7.html) make it easy to build with one JDK while testing on another.

## Multi-release JARs

Sometimes we want to take advantage of a newer JDK API when it is available, while still supporting an older baseline. [Multi-release JARs](https://openjdk.org/jeps/238) (Java 9) allow a JAR to contain alternative versions of classes under `META-INF/versions/<N>/`, which are used in preference to the base classes when running on Java *N* or later. This is a powerful technique, but it adds significant build and testing complexity, so it is best reserved for narrow, well-isolated cases (such as using virtual threads when available).

## Stay off JDK internals

Finally, a library that relies on JDK internals is a library that will break on a future JDK. The platform has been steadily strengthening its *integrity by default* guarantees: strong encapsulation of internals was enforced in Java 17 ([JEP 403](https://openjdk.org/jeps/403)), dynamically loading agents now produces warnings (Java 21, [JEP 451](https://openjdk.org/jeps/451)), memory-access methods in `sun.misc.Unsafe` are deprecated for removal and warn at runtime (Java 24, [JEP 498](https://openjdk.org/jeps/498)), and JNI usage is being restricted (Java 24, [JEP 472](https://openjdk.org/jeps/472)). If your library uses any of these, plan your migration to the supported replacements - such as `VarHandle` and the Foreign Function & Memory API - now, and tell users clearly about any command-line flags (such as `--enable-native-access`) that they need. The `jdeps --jdk-internals` tool will report any use of JDK internal APIs in your JAR.
