Modules came about in JDK 9 (via the [Java Platform Module System](https://openjdk.org/projects/jigsaw/spec/), or JPMS) as a means of modularizing Java itself, allowing for the first time the ability to explicitly prevent access to implementation code and to explicitly state what is public API. For many years prior to the release of Java 9, the developers of the JDK warned developers to not make use of APIs in some packages (most notably `com.sun.*`), because these were not considered part of the Java API and were implementation APIs (as we discuss in more detail in the [minimize API visibility](/jbp/jlbp-7.html) best practice). However, because Java lacked any visibility controls beyond the package level, any developer could access these implementation APIs, regardless of whether it was intended for public use or not, and regardless of the requests of the JDK developers. This proved to be a massive millstone around the neck of JDK developers as it prevented evolution of implementation classes, because they effectively became API. When JDK 9 shipped it included the concept of modules, and with modules came the ability to 'export' packages explicitly, with any package not exported effectively being invisible to users of that library. The JDK initially only warned about illegal access to its internals, but strong encapsulation was enforced by default in JDK 16 ([JEP 396](https://openjdk.org/jeps/396)) and the remaining escape hatch was removed in JDK 17 ([JEP 403](https://openjdk.org/jeps/403)). This caused real pain for parts of the Java ecosystem that depended on these implementation APIs, and it took several years to get things working again in some cases - but the result is a platform that is now able to evolve its internals far more freely.

## Overview

Despite the fact that Java modules were largely developed to modularize the Java platform itself, it does have some benefits for developers of libraries. Most notable is the ability to specify a module that explicitly exports some subset of the packages in the library, whilst keeping the others inaccessible to users of the library. This is achieved by way of a `module-info.java` file at the root of the library's source tree (i.e. in the unnamed root package, alongside the top-level package directories), taking the following form (by way of example using an Azure SDK for Java library):

```java
module com.azure.data.appconfiguration {
    requires transitive com.azure.core;

    exports com.azure.data.appconfiguration;
    exports com.azure.data.appconfiguration.models;
}
```

What you see here is that we have explicitly named this module `com.azure.data.appconfiguration`. Explicitly naming a module correctly is critical. Common practice is to use the same name as the base package for the library. In this case, all APIs are in the `com.azure.data.appconfiguration` base package, so it makes sense that this is also the module name.

On the next line you'll note that there is a transitive dependency on `com.azure.core`, which is the core library that all Azure SDK for Java libraries depend on. The `transitive` keyword tells the module system that any module that requires `com.azure.data.appconfiguration` should implicitly also be able to read `com.azure.core`. This is necessary because types from `com.azure.core` appear in the public API of `com.azure.data.appconfiguration`, and without it, users would have to add `requires com.azure.core` to their own module declaration. Use `requires transitive` for dependencies that appear in your public API, and plain `requires` for dependencies that are purely an implementation detail.

The last two lines are the most important - we are exporting two packages. All classes in these two packages (assuming the right access modifiers) are part of the public scope. All other packages, including sub-packages, are not within public scope.

## Other useful directives

A few other `module-info.java` directives are particularly useful for library developers:

* **`exports ... to ...`** (a *qualified export*) makes a package visible only to specific named modules. This is a clean way to share internal APIs between the modules of a multi-module library without making them available to everyone.
* **`opens`** grants deep reflective access to a package at runtime. Many frameworks (for example, JSON serialization libraries) need reflective access to model classes, and without `opens` they will fail on the module path.
* **`requires static`** declares a dependency that is needed at compile time but is optional at runtime - useful for optional integrations or annotation-only dependencies.
* **`uses` / `provides`** integrate with `java.util.ServiceLoader`, enabling pluggable implementations to be discovered at runtime.

## Important considerations

There are a few considerations to have if you are to introduce modules:

1. Module encapsulation is only enforced when a library is used on the *module path*. Many applications still place all of their dependencies on the classpath, in which case the `module-info.class` is ignored and all packages remain accessible. Modules are therefore a valuable additional safeguard, but they do not remove the need to clearly separate public and internal API by other means (as discussed in [minimize API visibility](/jbp/jlbp-7.html)). The `module-info.java` file is also only recognized by Java 9 and later.
2. Module names must be unique. Using the reverse domain name approach that Java has historically used for package naming works very well for module naming too.
3. Packages cannot be split over multiple modules. For example, you cannot have a `com.foo.bar` package in both module A and module B. It is allowable to have common package structure though, for example, module A can have `com.foo.bar` and module B can have `com.foo.bar.baz`.
4. Testing on the module path takes some care. Both Maven Surefire and Gradle support running tests on the module path, but white-box tests that live in the same packages as the code under test typically require the test classes to be patched into the module under test. Make sure that at least some of your tests (or a dedicated sample application) exercise the library as a real module, otherwise missing `exports` and `opens` directives will only be discovered by your users.

## If you can't add a module-info.java

If you are not yet in a position to add a full `module-info.java` (for example, because one of your dependencies cannot be used on the module path), the minimum you should do is reserve a stable module name by adding an `Automatic-Module-Name` entry to your JAR manifest:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-jar-plugin</artifactId>
  <configuration>
    <archive>
      <manifestEntries>
        <Automatic-Module-Name>com.example.mylibrary</Automatic-Module-Name>
      </manifestEntries>
    </archive>
  </configuration>
</plugin>
```

Without this, the module system derives an *automatic module name* from the JAR filename, which is fragile and may change between releases - breaking any users who have written `requires` clauses against it.
