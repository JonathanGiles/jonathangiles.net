Shading is the term given to the process of including dependencies within our JAR at build time, by copying an entire library out of its separate JAR file, renaming (or *relocating*) its packages, and updating code in our library to use the code in the shaded location, rather than at its original location. Tools such as the [Maven Shade Plugin](https://maven.apache.org/plugins/maven-shade-plugin/) and the [Shadow Gradle plugin](https://gradleup.com/shadow/) automate this process. When our library uses the shaded code, there is no longer any chance of diamond dependency conflicts, as it is now effectively an entirely separate codebase that is embedded within our library.

! This best practice is aimed at *library* developers. Building a single 'uber' or 'fat' JAR for a deployable *application* is a common and perfectly reasonable packaging choice, as nobody else depends on that JAR. The concerns below arise when the shaded artifact is itself a dependency of other people's code.

Shading can be an appealing solution to the problem of [diamond dependency conflicts](/jbp/jlbp-21.html), but it does come with its own set of problems. These include:

1. **We take away our users' ability to upgrade.** When we shade a dependency into our library, our users can no longer upgrade that dependency themselves if a concern arises, such as a security vulnerability. This moves the burden back to us to ensure that we are responsive and upgrade to the latest releases of our shaded libraries in as timely a manner as possible - for every supported version of our library.
2. **Shaded types must never appear in our public API.** Shading fundamentally creates new types in new package namespaces that duplicate the existing types. This means that we must not expose these types through any API that we write. If a user is given a `com.example.shaded.jackson.JsonNode`, it is incompatible with the `com.fasterxml.jackson.databind.JsonNode` they are already using elsewhere, and they now have two copies of every class to reason about in their IDE's auto-complete. This is [leaking types](/jbp/jlbp-7.html) at its worst.
3. **Vulnerabilities become invisible.** Most vulnerability scanners identify dependencies by their Maven coordinates or JAR metadata. Once a library has been shaded and relocated into our JAR, those scanners frequently fail to detect it at all, so our users may be running vulnerable code without any way of knowing. If we must shade, we should at a minimum publish an accurate [SBOM](/jbp/jbp-9.html) that lists the shaded components.
4. **Bloat and duplication.** If several libraries in an application each shade the same dependency, the application ends up with several copies of it, increasing the size of the application, its memory footprint, and its startup time.
5. **Things that rely on names break.** Relocation rewrites bytecode references, but it cannot always find every reference. Reflection using string class names, `ServiceLoader` configuration files in `META-INF/services`, logging configuration, serialization, and resource files can all break subtly after relocation. Shaded code can also interact poorly with the module system, as a shaded JAR must account for the `module-info.class` files of everything it embeds.
6. **Licensing obligations.** By shading, we are redistributing someone else's code inside our artifact. We must comply with its license, which typically means including its license and `NOTICE` files, and some licenses impose further requirements.

## What should we do instead?

Rather than reaching for shading as the default answer to dependency conflicts, consider the following alternatives first:

* **[Minimize dependencies](/jbp/jbp-2.html).** The best dependency to shade is the one we don't need at all. Check whether the JDK can now do the job, or whether [a little copying](/jbp/jbp-8.html) of a small, well-understood piece of code is a better trade-off.
* **Be a good citizen with the dependencies we do have.** Depend on widely-used, stable libraries with good compatibility track records, keep them [up to date](/jbp/jbp-4.html), and avoid exposing them in our public API, so that users have the freedom to choose the version that works for their application.
* **Publish a BOM.** If the conflicts are among our own libraries, [publishing a BOM](/jbp/jlbp-4.html) is the right fix.
* **Make integrations optional.** Rather than bundling a particular HTTP client or JSON library, define a small interface in our core library and provide implementations in separate, optional modules (discovered, for example, via `ServiceLoader`). Users only pull in the implementation they want. This is the approach taken by SLF4J for logging, and by the Azure SDK for Java for HTTP clients.

## If you must shade

Sometimes shading is the least-bad option - for example, when depending on a library with a poor compatibility track record, or when targeting environments where users cannot easily manage the classpath. If you do shade:

* Always relocate shaded packages into a namespace you own (e.g. `com.example.mylibrary.shaded.*`), so the shaded code cannot collide with the original library.
* Keep shaded code strictly internal: never expose shaded types in public API, and ideally don't export the shaded packages from your `module-info.java`.
* Shade as little as possible, using the minimization options of your shading tool and including only the libraries that truly need it.
* Remove the shaded dependencies from the published POM, so that users don't also pull in the unshaded versions transitively (the Maven Shade Plugin does this by default via its dependency-reduced POM).
* Document which libraries (and which versions) are shaded, publish an SBOM, and treat upgrades of shaded libraries as part of your security response process.
