As a developer there is nothing more frustrating than something breaking, whether it be our computer hardware, our network connection, the software we rely on to communicate and work, or the dependencies we rely on to build our software. When things break, our productivity grinds to a halt and we are forced to spend time getting things working again.

When we discuss breaking changes in the context of library development, we typically refer to 'breaking API changes' or 'breaking behavioural changes'. Regardless of the type of breaking being discussed, we should always treat these breakages as something that is undesirable. We should strive to never break, and if we must, then it must be for a very good reason. API and behavioural changes are breaking in very different ways, but fortunately we have tools available that can help reduce the amount of breaking that we do.

## Breaking API changes

A breaking API change is one where an API that you published is no longer available for users to call. User code that called this API will now no longer compile, and they will be forced to update their code and redeploy their application, if they wish to upgrade to your new API. Breaking API can occur for a number of reasons, such as:

* The API has been removed.
* If the API is a method:
  * The method name is changed, or
  * The parameter list has a change to the required set of parameters, or a change to the ordering of parameters, or
  * The return type is changed (even to a subtype, which is source compatible but binary incompatible), or
  * A checked exception is added to the `throws` clause.
* Renaming a class, or moving it to a different package.
* Adding an abstract method to an interface or abstract class that users may implement or extend (unless it has a `default` implementation).
* Reducing the visibility of a class, method, or field, or making a class or method `final`.

When it comes to breaking APIs, we really need to strive to do this as rarely as possible, so that we don't create unnecessary work on our users. In fact, our baseline expectation should be to never break our API, and only to allow it in exceptional situations. At the point we need to break, we then need to [follow semantic versioning rules](/jbp/jlbp-5.html).

Further best practices are outlined in the [characteristics of good API](/jbp/jlbp-1.html) guidance are related to evolvability, as well as in the [design for extensibility](/jbp/jlbp-9.html) best practice.

It is important to understand that Java has two distinct notions of compatibility. A change is *source compatible* if existing user code continues to compile against the new version, and *binary compatible* if existing, already-compiled user code continues to link and run against the new version without recompilation. These do not always align: changing a method's return type from `Object` to `String` is source compatible, but binary incompatible, because the JVM links methods by their exact descriptor. Binary compatibility matters enormously in the Java ecosystem, because our library will often be used by *other* libraries that were compiled against an older version, and which the end user cannot recompile. [Chapter 13 of the Java Language Specification](https://docs.oracle.com/javase/specs/jls/se25/html/jls-13.html) is the definitive reference on binary compatibility.

Fortunately, we do have tools on our side to keep us honest and aware of breaking API changes. These take the form of API analysis and change tracking tools such as [japicmp](https://siom79.github.io/japicmp/) and [Revapi](https://revapi.org/). They typically work by comparing a locally-built version of your library against the last released version found in Maven Central (or elsewhere), and can be configured to report or fail a build if source or binary incompatible changes have been detected (and have not been suppressed in the rare case where a breaking change has been deemed to be the correct thing to do). In my team at Microsoft, Revapi has proven to be a very useful tool, and I recommend everyone consider integrating it (or a similar tool) into your build process.

## Breaking behavioural changes

The other kind of breaking change that we need to be very careful of is changes in behaviour. For example, if the `foo()` method is documented to always return `42`, and users begin to depend on this behaviour, it would be very unwise to change it to instead return `0` in a future release. The obvious solution to prevent this from happening is to introduce good quality unit tests to validate expected behaviour, and to ensure this does not change unexpectedly between releases.

As mentioned in [configure build plugins](/jbp/jbp-6.html), we should make sure to introduce code coverage tooling such as JaCoCo to validate that we are writing tests that cover these critical behavioural aspects of our code. Reading the reports generated by tools such as JaCoCo, we can very quickly identify code paths that may not be getting enough test coverage, and writing tests for these paths can help prevent accidental behavioural breaking changes.

Finally, remember [Hyrum's Law](https://www.hyrumslaw.com/): users will come to depend on *undocumented* behaviour too - the iteration order of a returned `HashMap`, the exact text of an exception message, the thread on which a callback is invoked. We can't avoid every such change, but we can reduce the risk by documenting (and testing) what *is* guaranteed, by being explicit in our documentation about what is *not* guaranteed, and by calling out behavioural changes clearly in release notes.
