When we build libraries for others to use, we are often in the fortunate position where our work is entirely encapsulated within a single library. This makes communicating to users of our library about which version to use, when to upgrade, and how to deal with version conflicts much simpler. Sometimes though our projects aren't containable within a single library. Good examples that many people will be familiar with are the Spring, Micronaut, and Quarkus projects. Even the Azure SDK for Java ships separate libraries for different Azure services. The argument why projects do this is to reduce the surface area of a library into more comprehensible chunks of functionality, and by doing so making consumers of the library more productive and less overwhelmed with API and unnecessary dependencies.

Elsewhere on this website the guidance for Java developers is to [use BOMs whenever available](/jbp/jbp-1.html), with the reasoning being that it offloads the burden on the user to track the versions of their dependencies, and to ensure that their choice of version for each dependency is going to work well together. Any long-time Java developer will tell you that there is no joy in trying to match together dependencies so that their transitive dependency closure is able to work well together without runtime exceptions or other unexpected behavior.

## How do I create a BOM?

A BOM is merely another artifact that we need to get into the habit of [publishing to Maven Central](/jbp/jlbp-3.html), except it doesn't have any Java source code attached to it. Here's an abbreviated snippet from an early release of the [Azure SDK BOM](https://github.com/Azure/azure-sdk-for-java/tree/main/sdk/boms/azure-sdk-bom):

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">

  <modelVersion>4.0.0</modelVersion>
  <groupId>com.azure</groupId>
  <artifactId>azure-sdk-bom</artifactId>
  <version>1.0.4-beta.1</version>
  <packaging>pom</packaging>
  <name>Azure Java SDK BOM (Bill of Materials)</name>
  <description>Azure Java SDK BOM (Bill of Materials)</description>
  <url>https://github.com/azure/azure-sdk-for-java</url>
  <licenses>
    <license>
      <name>The MIT License (MIT)</name>
      <url>https://opensource.org/licenses/MIT</url>
      <distribution>repo</distribution>
    </license>
  </licenses>
  <developers>
    <developer>
      <id>microsoft</id>
      <name>Microsoft Corporation</name>
    </developer>
  </developers>
  <scm>
    <connection>scm:git:git://github.com/azure/azure-sdk-for-java</connection>
    <developerConnection>scm:git:git://github.com/azure/azure-sdk-for-java</developerConnection>
    <url>https://github.com/azure/azure-sdk-for-java</url>
  </scm>

  <properties>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <packageOutputDirectory>${project.build.directory}</packageOutputDirectory>
  </properties>

  <issueManagement>
    <system>GitHub</system>
    <url>https://github.com/azure/azure-sdk-for-java/issues</url>
  </issueManagement>

  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>com.azure</groupId>
        <artifactId>azure-core</artifactId>
        <version>1.17.0</version>
      </dependency>
      <dependency>
        <groupId>com.azure</groupId>
        <artifactId>azure-core-http-netty</artifactId>
        <version>1.10.0</version>
      </dependency>
      <dependency>
        <groupId>com.azure</groupId>
        <artifactId>azure-cosmos</artifactId>
        <version>4.16.0</version>
      </dependency>
      <dependency>
        <groupId>com.azure</groupId>
        <artifactId>azure-storage-blob</artifactId>
        <version>12.12.0</version>
      </dependency>
      <!-- ... many more ... -->
    </dependencies>
  </dependencyManagement>
</project>
```

This is a standard BOM file - you'll observe that it is configured exactly the same as a standard Maven POM, and that is because this is all it is! The only major distinction is that the `packaging` value is `pom`, rather than the more common `jar`.

Releasing a BOM uses the same release processes that we use today for releasing any other artifact. Maven Central will accept a BOM without any additional configuration (although note that, as a POM-only artifact, it does not need the sources and JavaDoc JARs that Maven Central otherwise requires).

A BOM should contain *only* a `dependencyManagement` section. In particular, avoid making your BOM the parent POM of your libraries, or including build configuration, properties, or plugin management in it - these leak into, and can interfere with, the builds of your users.

Gradle users can produce and publish a BOM using the [Java Platform plugin](https://docs.gradle.org/current/userguide/java_platform_plugin.html):

```kotlin
plugins {
    `java-platform`
    `maven-publish`
}

dependencies {
    constraints {
        api("com.example:my-library-core:1.4.0")
        api("com.example:my-library-extras:1.4.0")
    }
}

publishing {
    publications {
        create<MavenPublication>("bom") {
            from(components["javaPlatform"])
        }
    }
}
```

## BOM Challenges

### What to include

There are different ways to approach a BOM. We could consider ourselves the owner of the universe of libraries, adding every known library we can into our BOM, even if they fall outside of our ownership as library developers. Alternatively, we could only include libraries in our BOM that are directly developed by ourselves. There are pros and cons to each approach, but from my experience, it is better to consider a BOM a look-up for libraries that only you provide. Going beyond this and including other libraries has a tendency to result in classpath collisions at runtime that are undesirable, and also often hard to resolve. (Application frameworks such as Spring Boot are a notable exception: their BOMs deliberately manage a curated set of third-party libraries, because the framework *is* the platform the application is built on.)

### Versioning, and breaking changes in listed libraries

Before you start to release a BOM it is important to consider how it will be versioned. A BOM is itself an API: users write code against the set of library versions that it selects. Upgrading a BOM silently upgrades *every* library the user depends on from that BOM, so a BOM upgrade can be a breaking change even though the BOM contains no code at all.

A BOM can only list one version of any given `groupId:artifactId`. This is the heart of the problem: when one listed library releases a new major version with breaking changes, the BOM cannot offer both the old and the new version. Whatever version the BOM picks is forced onto every user who upgrades the BOM, including users who are not ready to migrate.

My recommendation is that a BOM should follow [semantic versioning](/jbp/jlbp-5.html) based on the effect that upgrading it has on its users:

* **Major** - any listed library moves to a new major version, a library is removed from the BOM, a library changes its coordinates, or a listed library raises its [Java baseline](/jbp/jlbp-20.html). Any of these can break a user who simply bumps the BOM version.
* **Minor** - new libraries are added to the BOM, or listed libraries move to new minor versions.
* **Patch** - listed libraries only receive patch releases.

A BOM must also never *downgrade* a library between releases, as users who upgrade the BOM would quietly lose fixes they already had.

There are some practical consequences of this policy:

* **A BOM major version tells users that *something* broke, not *what* broke.** A user who only uses one library from the BOM is told that the upgrade is breaking, even though their library may be unchanged. Release notes for every BOM release should therefore list which constituent libraries changed major version, with links to their migration guides.
* **Frequent BOM major versions are a warning sign.** If the constituent libraries release breaking changes on unrelated schedules, the BOM will be forced to change major version constantly, and users will learn to ignore it (or stop upgrading). This is an organizational problem rather than a BOM problem. Libraries that share a BOM should agree to [resist breaking changes](/jbp/jlbp-6.html), and to batch the breaking changes that are unavoidable into coordinated, infrequent, well-announced releases.
* **You may choose to hold back a new major version.** It is legitimate for a BOM to keep listing the old major version of a library for a while (continuing to pick up its patch releases), so users can migrate on their own schedule by explicitly overriding the version, before the BOM itself moves on in its next major release.
* **New coordinates make breaking changes much easier.** If a library's new major version uses a new `groupId` (or `artifactId`) *and* a new Java package name, then the old and new versions are, as far as Maven and the JVM are concerned, entirely different libraries. The BOM can list both, and users (and their transitive dependencies) can migrate gradually. This is the approach taken by Jackson 3 (`tools.jackson.*`, replacing `com.fasterxml.jackson.*`), Apache Commons Lang 3 (`org.apache.commons.lang3`), and Apache HttpClient 5 (`org.apache.hc.client5`). See [avoid diamond dependency conflicts](/jbp/jlbp-21.html) for more on why this matters.

Some projects use calendar versioning for their BOMs instead (Spring Cloud release trains, for example, are versioned like `2025.0.0`). This works well when the BOM is released on a predictable schedule, but note that a calendar version conveys nothing about compatibility, so the release notes must carry that burden instead.

### Converging the transitive closure

The hardest part of maintaining a BOM is not choosing the versions of *our own* libraries. It is ensuring that, once those versions are chosen, the full transitive dependency graph of everything in the BOM converges on a single compatible version of every *third-party* library.

Consider a BOM listing two of our libraries, `foo-storage` and `foo-messaging`, both depending on Netty and Jackson. If `foo-storage` was last released three months ago, its POM was frozen at the versions of Netty and Jackson that were current three months ago. If `foo-messaging` was released last week, it has newer versions. A user who depends on both now has a [diamond dependency](/jbp/jlbp-21.html): Maven picks one version of Netty (the "nearest" one in the dependency tree - which is often not the newest), Gradle picks the highest, and one of our libraries ends up running against a version of Netty it was never tested with. If that version is incompatible, the result is a `NoSuchMethodError` or `NoClassDefFoundError` at runtime - a failure that no amount of compile-time checking would have caught.

The BOM gave the user a consistent set of *our* libraries, but not a consistent *closure*. Some ways to close the gap are:

* **Use a single source of truth for third-party versions.** All libraries that ship in the BOM should be built against the same versions of shared dependencies, managed in one place (a shared parent POM, a Gradle version catalog, or a versions file in a monorepo), so that libraries cannot drift apart.
* **Release together where possible.** The longer a library goes without a release, the more stale its dependency versions become relative to its siblings. A regular release train - even if some libraries only receive dependency updates - keeps the closure converged. (The Azure SDK for Java, for example, releases its libraries on a shared monthly cadence.)
* **Verify the closure before every BOM release.** Create a test project that depends on the BOM and on *every* library listed within it, and fail the build if the closure does not converge. In Maven, the [Enforcer plugin](https://maven.apache.org/enforcer/enforcer-rules/index.html) `dependencyConvergence` and `requireUpperBoundDeps` rules do this. In Gradle, `configurations.all { resolutionStrategy.failOnVersionConflict() }` does the same. Google's [Linkage Checker](https://github.com/GoogleCloudPlatform/cloud-opensource-java/tree/main/linkage-checker) goes further, checking that every class and method referenced in the closure actually exists. Then run the test suites of the listed libraries against that resolved closure, rather than only against the versions each library was originally released with.
* **Think carefully before managing third-party versions in the BOM.** It can be tempting to "fix" convergence by adding Netty, Jackson, etc. to our BOM's `dependencyManagement`. This does force convergence, but it also means our BOM now fights with every other BOM the user imports (for example, Spring Boot's), with the winner decided by the [order in which the BOMs are imported](/jbp/jbp-1.html). As discussed in *What to include*, a library BOM should usually manage only our own libraries, and convergence should be achieved by aligning the libraries themselves.
* **Never remove a library to make the closure converge.** Removing an entry breaks every user who relied on the BOM to provide its version. If the closure cannot be made clean for a release, ship the BOM anyway, document the known conflict and its workaround, and fix it in the next release.

### Release concerns

A BOM is intended to unify libraries from a single project under a common banner to help our users be more productive. Sometimes these libraries can be developed by separate teams whose release frequencies are not as in sync as ideal. This can lead to pressures on when and how to release a BOM. For example, questions we will need to answer include:

* Should a BOM release occur on a regular cadence or whenever a constituent library is updated?
* Should we include dependencies in our BOM that are in development (e.g. that are considered alpha, beta, preview, RC, or equivalent)?
* What do we do if the transitive closure of the BOM does not converge for a release?

Teams will arrive at different answers for these questions, but to give direction based on experiences here at Microsoft, we have decided on the following:

* BOMs will be released regularly. We decided to release monthly, as this aligned with our monthly release cadence for all Azure SDK for Java client libraries.
* We decided to not include in-development libraries in our BOM.
* We wrote tooling that keeps us informed constantly on the state of the transitive closure of our next BOM release. We try our best to ensure that the next release of all Azure SDK for Java client libraries aligns on their dependency versions. However, if we cannot fully get to a state that is clean, we never remove a dependency from the BOM, as this will have the effect of breaking people who upgrade to a new BOM and find that a dependency version cannot be determined any longer.

### Communication

Once a BOM is released, the next challenge is communicating its availability to all developers. You preferentially want developers to use this in all projects, and you never want to see developers specifying versions of dependencies that are listed within the BOM. In all places where Maven (or Gradle, etc) coordinates are listed for a library that you own, you want to preface it by encouraging users to use the BOM instead. For example, you might do something similar to what is documented for the `azure-cosmos` library [here](https://github.com/Azure/azure-sdk-for-java/tree/main/sdk/cosmos/azure-cosmos#getting-started).

## Conclusion

In summary, a BOM is not a trivial amount of work, particularly if you want to improve the lives of developers using your libraries. A BOM should be viewed as a means of reducing developer friction, offloading burden from them and moving it onto yourself. When we remove friction like this, we are more likely to delight our users, and enable them to become advocates for our libraries and any services that they represent.
