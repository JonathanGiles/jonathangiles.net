A build is *reproducible* if anyone who builds the same source code, with the same build tools, gets bit-for-bit identical output. For a library published to [Maven Central](/jbp/jlbp-3.html), this is a powerful property: it allows anyone to check independently that the JAR they downloaded really was built from the tagged source code in your repository, and not from a modified copy on a compromised build machine. It turns "trust us" into "check for yourself".

The practices in [secure your software supply chain](/jbp/jbp-9.html) apply to every Java developer. This best practice goes into more detail for library developers, who publish artifacts that many other people depend on.

## Why it matters for libraries

* **Verification.** Attacks on build infrastructure (rather than source code) are among the hardest supply chain attacks to detect. If a release can be rebuilt and compared, a tampered artifact stands out.
* **Independent rebuilders.** Projects such as [Reproducible Central](https://github.com/jvm-repo-rebuild/reproducible-central) rebuild releases from Maven Central and publish whether each one matched, so users (and their security tooling) can see which libraries are verifiably built from source.
* **Better engineering.** A reproducible build is one where you know exactly what goes into your artifacts. It makes it possible to confirm that two builds are the same, to see exactly what changed between two releases, and to make better use of build caches.

## Make the build reproducible

Modern versions of Maven and Gradle do most of the work. The main remaining source of difference is timestamps recorded in archives:

* **Maven:** set the `project.build.outputTimestamp` property, and use recent versions of all plugins (older plugin versions may not respect it). The Maven Release Plugin updates the property automatically when releasing.

```xml
<properties>
  <project.build.outputTimestamp>2026-01-01T00:00:00Z</project.build.outputTimestamp>
</properties>
```

* **Gradle:** archive tasks are reproducible by default as of Gradle 9. On earlier versions, configure every archive task with `isPreserveFileTimestamps = false` and `isReproducibleFileOrder = true`.

## Remove the remaining sources of variation

Once timestamps are fixed, differences usually come from one of the following:

* **The JDK.** Different major versions of `javac` can produce different bytecode, so release with a fixed, recorded JDK version (for example, via a Maven or Gradle toolchain, or a pinned CI image), regardless of the [Java baseline](/jbp/jlbp-20.html) your library targets.
* **Generated content.** Code generators, annotation processors, and build scripts that embed the current date and time, the user or host name, absolute file paths, or iterate over a `HashMap` or the file system in an unspecified order. A generated `version.properties` file containing a build timestamp is a very common culprit.
* **The environment.** Line endings (beware of Git's `core.autocrlf` on Windows), file permissions, locale, and time zone can all leak into build output.
* **Floating versions.** A build that resolves a [floating dependency or plugin version](/jbp/jbp-3.html) can produce different output from one day to the next.

## Verify it

Don't assume the build is reproducible - check:

* For Maven, the [Maven Artifact Plugin](https://maven.apache.org/plugins/maven-artifact-plugin/) offers `artifact:check-buildplan`, which warns about plugins known to be non-reproducible, and `artifact:compare`, which rebuilds the project and compares the output against a reference (such as the copy already in Maven Central).
* Build the same commit twice, ideally on different machines (or in CI and locally), and compare the results. Tools such as [diffoscope](https://diffoscope.org/) show exactly what differs.
* Add a CI job that performs this check regularly, so that reproducibility doesn't silently regress.

Finally, tell your users: document that your releases are reproducible, how to rebuild them, and which JDK and build tool versions you used. Consider adding your project to [Reproducible Central](https://github.com/jvm-repo-rebuild/reproducible-central), so that your releases are independently rebuilt and verified.
