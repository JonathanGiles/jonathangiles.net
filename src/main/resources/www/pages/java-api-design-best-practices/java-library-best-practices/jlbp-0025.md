When an application misbehaves in production, the first questions are usually "where did the time go?" and "what failed?". If the answer lies inside our library - a slow network call, a retry storm, a connection pool that ran dry - users can only see it if our library tells them. [OpenTelemetry](https://opentelemetry.io/) (OTel) has become the industry-standard, vendor-neutral way to do that, with support from essentially every observability vendor and open source backend.

Applications can get a lot of telemetry for free from the [OpenTelemetry Java agent](https://opentelemetry.io/docs/zero-code/java/agent/), which instruments many popular libraries using bytecode manipulation. But the agent only knows about libraries that someone has written instrumentation for, its instrumentation lives outside the library and can lag behind it, and many users can't or won't run a Java agent. *Native* instrumentation, written by the library authors using the OpenTelemetry API, is generally the better outcome: it is always in sync with the library, it can describe what the library is really doing, and it works everywhere.

## Depend only on the API

OpenTelemetry is deliberately split into an *API* and an *SDK*. Libraries must depend only on the API (`io.opentelemetry:opentelemetry-api`), and never on the SDK or any exporter. The application decides whether to install an SDK, how to configure it, and where to send the data. If no SDK is installed, every API call is a cheap no-op, so a library that is instrumented costs essentially nothing for users who don't use OpenTelemetry.

The OpenTelemetry Java API is stable and has strong backward-compatibility guarantees, which makes it a reasonable [dependency](/jbp/jbp-2.html) for a library. Even so, consider making it an optional dependency, or putting the instrumentation in a separate module, if your library is used in environments where every dependency is scrutinized.

## Let users provide the `OpenTelemetry` instance

Accept an `OpenTelemetry` instance through the library's builder or configuration. Falling back to `GlobalOpenTelemetry.get()` when none is provided means things work out of the box, but some applications (and many tests) deliberately run more than one configuration in the same JVM, and can only do so if they can pass an instance in explicitly.

Name the tracer and meter after your library (typically its root package or Maven coordinates), and include the library's version, so that users can tell exactly which library and version produced each piece of telemetry:

```java
public final class StorageClient {
    private final Tracer tracer;

    StorageClient(OpenTelemetry openTelemetry) {
        this.tracer = openTelemetry.tracerBuilder("com.example.storage")
            .setInstrumentationVersion(StorageVersion.VERSION)
            .build();
    }

    public Blob download(String name) {
        Span span = tracer.spanBuilder("download")
            .setSpanKind(SpanKind.CLIENT)
            .setAttribute("example.storage.blob.name", name)
            .startSpan();
        try (Scope scope = span.makeCurrent()) {
            return doDownload(name);
        } catch (RuntimeException e) {
            span.recordException(e);
            span.setStatus(StatusCode.ERROR);
            throw e;
        } finally {
            span.end();
        }
    }
}
```

## Follow the semantic conventions

OpenTelemetry's [semantic conventions](https://opentelemetry.io/docs/specs/semconv/) define standard names for spans, attributes, and metrics for common operations - HTTP requests, database calls, messaging, RPC, and more. Observability tools build dashboards and alerts on top of these names, so following them means users get useful views of our library's behaviour without any extra work. Use the published conventions wherever one applies, and give attributes that are specific to your library a clear, namespaced name of their own.

## Instrument at the right level

Not every method call deserves a span. Create spans for the operations that matter to users - a logical call to a remote service, a message sent or received - and avoid spans for internal helper methods, which only add noise and cost.

Be mindful of layers. If our library sits on top of an HTTP client that is itself instrumented, then our span should describe the logical operation (for example, "upload blob"), and the HTTP client's spans will appear beneath it, one per attempt. This makes retries visible. Avoid creating a second, duplicate span for the same HTTP call.

Metrics are often more useful (and much cheaper) than spans for high-volume operations. Histograms of operation duration, and counters or gauges for things like connection pool usage and retry counts, give users a view of the library's health over time.

## Propagate context

OpenTelemetry tracks the "current" span using a `Context`, which by default is stored in a thread-local. If our library hands work off to another thread - an executor, a callback, an async completion - the context is lost unless we carry it across, and users see disconnected traces. Wrap executors with `Context.taskWrapping(executor)` (or wrap individual tasks with `Context.current().wrap(runnable)`), and make sure user callbacks run in the context of the operation that triggered them.

If the library makes calls to remote services, use the configured propagators (`openTelemetry.getPropagators()`) to inject trace context into outgoing requests (for example, as a W3C `traceparent` HTTP header), so that traces continue across service boundaries.

## Mind what you record

Telemetry is frequently exported to third-party systems and retained for a long time. Never record secrets, credentials, or tokens, and be cautious about recording user data or personally identifiable information. Avoid attributes with unbounded values (such as full URLs with query strings, or user IDs) on *metrics*, as each unique value creates a new time series and can be very expensive for users.

## Logging

For logs, continue to use a [logging API](/jbp/jbp-5.html) such as SLF4J or `System.Logger`. OpenTelemetry provides bridges for the common logging backends, which add trace and span IDs to log records automatically, so that users can correlate log messages with the trace that produced them. Libraries don't need to (and shouldn't) emit logs through the OpenTelemetry API directly.
