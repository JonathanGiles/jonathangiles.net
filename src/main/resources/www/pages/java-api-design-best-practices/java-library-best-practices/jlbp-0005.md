Semantic versioning is a [well-specified convention](https://semver.org/) used by many software projects, although admittedly the extent to which the convention is followed can vary considerably between projects. In essence, semantic versioning results in a version number that takes the form `MAJOR.MINOR.PATCH`, and from this we can articulate to users the extent of any changes in our library based on our incrementing of these values.

Developers should increment these values based on the following rules:

1. Increment the `MAJOR` version when you make incompatible API changes,
2. Increment the `MINOR` version when you add functionality in a backwards compatible manner, and
3. Increment the `PATCH` version when you make backwards compatible bug fixes.

When semantic versioning is followed, users of our libraries can clearly discern the amount of caution that they should proceed with if they wish to upgrade to a newer version of a library. Upgrading to a higher patch version can be considered with relative ease, whereas upgrading to a higher major version should proceed with caution and much more testing.

## Java-specific considerations

* **'Incompatible' includes binary incompatibility.** In Java, a change can be source compatible (user code still compiles) but binary incompatible (already-compiled user code fails at runtime with a `NoSuchMethodError` or similar), or vice versa. Both must be treated as breaking changes for the purpose of semantic versioning. Because transitive dependencies are compiled against specific versions of your library, binary compatibility is arguably the *more* important of the two. See [resist breaking changes](/jbp/jlbp-6.html) for tooling that can detect both.
* **Raising the minimum Java version is a breaking change.** Users who are still on the previous minimum Java version will be unable to use the new release, so this should be treated as a major version increment (or, at minimum, very clearly communicated). See [choose your Java baseline deliberately](/jbp/jlbp-20.html).
* **Pre-release versions.** Semantic versioning allows pre-release labels such as `2.0.0-beta.1`. These are a great way to gather feedback on new API before committing to it. Be aware that Maven's version ordering differs slightly from the semantic versioning specification in some edge cases, so stick to simple, well-understood qualifiers such as `alpha`, `beta`, and `rc` with a numeric suffix.
* **`0.x` versions.** Semantic versioning states that anything may change at any time in a `0.x` release. This is useful during initial development, but many projects linger in `0.x` for years, despite being used in production. If people depend on your library in production, it is time to commit to a `1.0.0` release and the compatibility promises that come with it.

For more details on all considerations that must be made as part of following proper semantic versioning conventions, refer to the details at [https://semver.org/](https://semver.org/).
