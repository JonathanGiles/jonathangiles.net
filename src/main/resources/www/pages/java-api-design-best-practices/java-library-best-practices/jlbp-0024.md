[GraalVM Native Image](https://www.graalvm.org/latest/reference-manual/native-image/) compiles a Java application ahead-of-time into a standalone native executable. The result starts in milliseconds and uses a fraction of the memory of the same application on the JVM, which makes it attractive for command-line tools, serverless functions, and densely-packed containers. Spring Boot, Quarkus, Micronaut, and Helidon all support building native images, and many of their users do.

Native image works under a *closed-world assumption*: at build time, it analyzes the application to determine every class, method, and field that can possibly be reached, and only those are included in the executable. Anything that is discovered dynamically at run time - reflection, dynamic proxies, resources loaded by name, JNI, serialization - is invisible to this analysis unless the application tells native image about it in advance. When it isn't told, the result is a native executable that builds successfully and then fails at run time, often with a confusing `ClassNotFoundException` or a missing resource.

Every library on the classpath contributes to this problem or solution. Application developers can work around a library that doesn't support native image, but it is painful, fragile work. Library developers are in the best position to fix it once, for everyone.

## Prefer code that native image can see

The best native image support is the kind that needs no configuration at all. Native image can see a great deal: it handles reflection and resource lookups whose arguments are constants it can work out at build time, and `ServiceLoader` lookups declared in `module-info.java` or `META-INF/services`. It cannot see through strings that are built at run time, read from configuration files, or passed in by the user.

* Prefer direct code over reflection. Generate code at compile time (for example, with an annotation processor) rather than discovering classes, fields, and methods reflectively at run time.
* Use `ServiceLoader` for plugins, rather than scanning the classpath or instantiating classes from names in configuration files.
* Avoid relying on classpath scanning, which does not work in a native image.
* Keep static initializers free of side effects. Avoid starting threads, opening files or sockets, reading environment variables, or seeding random number generators in a `static {}` block, so that classes can safely be initialized at build time if the application chooses to.

These practices also make libraries friendlier to [Project Leyden](https://openjdk.org/projects/leyden/) ahead-of-time caching in the JDK itself (introduced in Java 24 with [JEP 483](https://openjdk.org/jeps/483) and extended in Java 25), which rewards the same predictable, analyzable start-up behaviour.

## Ship reachability metadata in your JAR

Where dynamic behaviour can't be avoided, describe it with *reachability metadata*. Native image automatically picks up metadata found inside JARs on the classpath at `META-INF/native-image/<groupId>/<artifactId>/`. Recent GraalVM releases use a single `reachability-metadata.json` file covering reflection, resources, JNI, proxies, and serialization:

```json
{
  "reflection": [
    {
      "type": "com.example.storage.implementation.BlobProperties",
      "allDeclaredFields": true,
      "allDeclaredConstructors": true
    }
  ],
  "resources": [
    { "glob": "com/example/storage/storage.properties" }
  ]
}
```

Metadata that ships in your JAR is always in sync with your code. Keep it as narrow as possible: register the specific types and members that are needed, and use conditions (which apply metadata only when a given type is reachable) rather than registering everything up front.

You don't need to write metadata entirely by hand. The [tracing agent](https://www.graalvm.org/latest/reference-manual/native-image/metadata/AutomaticMetadataCollection/) (`-agentlib:native-image-agent=config-output-dir=...`) records the dynamic accesses made while running on the JVM - for example, while running your test suite - and writes them out as metadata. Treat its output as a starting point to review and trim, not something to commit blindly.

The community-run [GraalVM Reachability Metadata Repository](https://github.com/oracle/graalvm-reachability-metadata) provides metadata for many popular libraries that don't ship their own. It is a useful stopgap, but metadata maintained by someone else for a specific version of your library will always lag behind your releases. Shipping metadata in your own JAR is far better.

## Test in native mode

Native image support that isn't tested will break. The [GraalVM Native Build Tools](https://graalvm.github.io/native-build-tools/latest/index.html) provide a Maven plugin (`org.graalvm.buildtools:native-maven-plugin`) and a Gradle plugin (`org.graalvm.buildtools.native`) that can compile your JUnit tests into a native executable and run them (`mvn -Pnative test` or `gradle nativeTest`). Native compilation is slow and memory-hungry, so it is common to run these tests in a separate CI job, or nightly, rather than on every commit - but do run them before every release.

## Document what is supported

Tell your users whether your library supports native image, which features (if any) don't work, and anything they need to configure in their application. If you rely on a framework's ahead-of-time processing (such as Spring's AOT engine or a Quarkus extension), say so, and say whether the library also works in a plain native image without that framework.
