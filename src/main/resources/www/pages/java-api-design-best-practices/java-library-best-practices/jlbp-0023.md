Virtual threads, finalized in Java 21 ([JEP 444](https://openjdk.org/jeps/444)), are one of the most significant changes to the Java platform in years. They make threads cheap enough that an application can create one per task - millions of them, if need be - and write simple, blocking, easy-to-debug code that still scales. Frameworks such as Spring Boot, Quarkus, Helidon, and Micronaut can all run request handling on virtual threads, and many applications now do so by default.

This has consequences for library developers. Our libraries are increasingly called *from* virtual threads, whether we planned for it or not, and code that was perfectly reasonable in a world of a few hundred expensive platform threads can behave badly in a world of a million cheap ones. The good news is that being virtual thread friendly mostly means writing *simpler* code, not more complex code.

## Prefer simple blocking APIs

For many years, the only way to build a scalable client library was to offer an asynchronous API, using `CompletableFuture` or a reactive library, because blocking a platform thread on I/O was too expensive. Virtual threads change this calculation: blocking a virtual thread is cheap, so a straightforward synchronous API now scales well for most workloads.

If you are designing a new library, start with a synchronous API, and add an asynchronous one only if you have users who genuinely need it. If you already offer both, keep them [consistent](/jbp/jlbp-12.html), but don't feel that every new feature must be built async-first. Above all, never implement a synchronous API by blocking on the asynchronous one (for example, `future.join()` or `mono.block()`) - this doubles the work, and frequently hides context and stack traces from users.

## Don't pin the carrier thread

A virtual thread runs by being mounted on a platform *carrier* thread. When a virtual thread blocks, it normally unmounts, freeing the carrier to run other virtual threads. In some situations, however, the virtual thread is *pinned* to its carrier and cannot unmount while blocked, which (with only a handful of carriers) can starve the whole application of throughput, or even deadlock it.

* **`synchronized` on Java 21 to 23.** On these releases, blocking inside a `synchronized` block or method pins the carrier. [JEP 491](https://openjdk.org/jeps/491) removed this limitation in Java 24, so it does not apply on Java 25. However, if your [Java baseline](/jbp/jlbp-20.html) is Java 21, your users may still be running on it. Where your library performs blocking I/O or waits while holding a lock, consider using a `java.util.concurrent.locks.ReentrantLock` rather than `synchronized`. Short, non-blocking `synchronized` sections are fine on every release.
* **Native code.** A virtual thread that calls into native code (via JNI or the Foreign Function & Memory API) and blocks there remains pinned on every Java release. If your library makes long-running native calls, document this, and consider running them on a dedicated platform thread.

Pinning can be detected with the `jdk.VirtualThreadPinned` [JDK Flight Recorder](https://docs.oracle.com/en/java/javase/25/jfapi/) event, which is enabled by default and records stack traces of pinned threads that block for longer than a threshold. Run your test suite on virtual threads with JFR enabled, and look for these events.

## Let users supply the threads

Libraries often need to run work in the background: timers, callbacks, connection pools, and so on. Rather than creating our own thread pools internally, let users provide an `Executor` (or a `ThreadFactory`) through the library's builder or configuration, so they can choose to use `Executors.newVirtualThreadPerTaskExecutor()` - or not. When the user doesn't provide one, choose the default carefully, and give any threads you do create clear names.

## Don't use thread pools to limit concurrency

A common pattern in older code is to bound concurrency by bounding a thread pool: "we never make more than 20 concurrent requests, because the pool only has 20 threads". With virtual threads, users will not pool threads at all - there is no reason to - so this implicit limit disappears. If a resource genuinely needs a concurrency limit (a connection pool, a rate-limited service, a fixed amount of memory), enforce it explicitly, for example with a `java.util.concurrent.Semaphore`.

## Be careful with `ThreadLocal`

`ThreadLocal` works with virtual threads, but its most common use in libraries - caching an expensive object (a `MessageDigest`, a `SimpleDateFormat`, a large buffer) per thread so that it can be reused - no longer makes sense when every task runs on its own short-lived thread. The cache will be created and discarded on every task, and with a million threads alive at once, it can consume a surprising amount of memory. Prefer immutable, thread-safe alternatives (such as `java.time.format.DateTimeFormatter`), a bounded object pool, or simply allocating the object when it is needed.

For passing context down a call stack (such as a request ID or a security principal), Java 25 finalized [scoped values](https://openjdk.org/jeps/506) (`java.lang.ScopedValue`), which are immutable, bounded to a scope, and far cheaper than `ThreadLocal` when used with large numbers of virtual threads. They are a good choice for libraries whose baseline is Java 25. [Structured concurrency](https://openjdk.org/jeps/505), which pairs well with scoped values, is still a preview API in Java 25, so libraries should not yet expose it in their public API.

## Test on virtual threads

The only reliable way to know that a library behaves well on virtual threads is to test it on them. Run (at least some of) your concurrency, integration, and load tests with work submitted to `Executors.newVirtualThreadPerTaskExecutor()`, on both your minimum supported Java release and the latest one, and watch for pinning events, deadlocks, and memory growth.
