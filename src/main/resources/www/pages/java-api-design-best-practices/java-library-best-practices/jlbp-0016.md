Boxing / Unboxing is when Java converts primitives to and from their wrapper (reference) types, for example, converting between `int` and `Integer` types. This is often done automatically through the process known as autoboxing. There are three concerns when using reference types:

1. Increased possibility of null pointer exceptions (compared with no possibility with primitives).
2. Correctness (e.g. the equality operator `==` works differently for `int` and `Integer`).
3. Performance considerations.

The correctness concern is particularly insidious, because it can appear to work in testing:

```java
Integer a = 127, b = 127;
System.out.println(a == b);   // true - small values are cached

Integer c = 128, d = 128;
System.out.println(c == d);   // false - compares references, not values!
```

As noted in the [Java language documentation on autoboxing](https://docs.oracle.com/javase/8/docs/technotes/guides/language/autoboxing.html):

>It is not appropriate to use autoboxing and unboxing for scientific computing, or other performance-sensitive numerical code. An Integer is not a substitute for an int; autoboxing and unboxing blur the distinction between primitive types and reference types, but they do not eliminate it.

For these reasons, when we write API it is important that we consider the necessity of any API that returns or accepts wrapper types, as opposed to primitive types. Whenever possible, wrapper types should be replaced with primitive types.

The JDK provides primitive specializations of many common APIs specifically to avoid boxing, and we should use (and, where appropriate, offer) them in our own APIs:

* `IntStream`, `LongStream`, and `DoubleStream` rather than `Stream<Integer>` etc.
* `OptionalInt`, `OptionalLong`, and `OptionalDouble` rather than `Optional<Integer>` etc.
* Primitive functional interfaces such as `IntFunction`, `ToIntFunction`, `IntPredicate`, and `IntSupplier` (see [understand functional interfaces](/jbp/jlbp-17.html)).

A legitimate reason to use a wrapper type is when `null` is a meaningful value, such as an optional numeric setting on an [options type](/jbp/jlbp-9.html) where `null` means 'use the default'. Even then, consider whether an `OptionalInt` return type or a clearly documented sentinel would serve users better, and be very wary of `Boolean` used as a tri-state (`true`, `false`, or `null`) - it is almost always clearer to use an `enum`.

Looking further ahead, [Project Valhalla](https://openjdk.org/projects/valhalla/) is working to narrow the gap between primitives and objects with value classes, which may in time reduce the cost of boxing. Until it is delivered in a Java release you can baseline on, the guidance above stands.
