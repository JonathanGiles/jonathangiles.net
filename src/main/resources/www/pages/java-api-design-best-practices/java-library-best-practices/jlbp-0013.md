The phrase '[eating your own dog food](https://en.wikipedia.org/wiki/Eating_your_own_dog_food)' is an interesting one admittedly, but it conjures up the right imagery when it comes to ensuring that our APIs are suited for the stated purpose. We should consider it a fundamental failing of our development process if we aren't the first customers of our libraries, and this should begin well in advance of our libraries being made publicly available. Ideally this would be an ongoing process throughout the development of our library.

It is important that we accept however that we are not the best testers of our software, because we carry with us intimate knowledge of the problem domain, as well as how our library works to represent this. We need to find people less familiar with the problem domain and our code. These might be people on adjacent teams to ourselves, or friendly customers who are happy to give us honest feedback. In the Azure SDK team, we ran regular *user studies*, in which developers unfamiliar with a library were given a set of tasks to complete with it, while we silently observed where they struggled. These sessions were frequently humbling, and invariably resulted in API improvements that we would never have identified on our own.

We need to discern two things from these studies with developers who are unfamiliar with our API:

1. Can the user perform the tasks that the API sets out to enable?
2. Is our API concise, or does our user find themselves struggling with an overwhelming morass of API that goes beyond the stated purpose of our library? In other words, have we failed to be [restrained](/jbp/jlbp-1.html)?

## Practical ways to dog food

* **Write the samples first.** Before writing an implementation, write the code you expect a user to write to accomplish the key scenarios of your library. If the sample code is awkward, the API is awkward - and it is far cheaper to discover that before the implementation exists.
* **Write tests from the outside.** Keep a set of tests that only use the public API, in a separate package (or module) from the implementation. If these tests need to reach into internals, so will your users.
* **Use pre-release versions.** Ship `beta` releases (see [use semantic versioning](/jbp/jlbp-5.html)) and actively seek feedback on them, so that API changes can still be made before the API is locked down.
* **Be your own first customer.** Where possible, build something real with your library - an internal tool, a sample application, or another library that depends on it.
