We should [resist breaking changes](/jbp/jlbp-6.html), but sometimes they really are the right call. When we do release a new major version, every one of our users has to do some work to upgrade - and the harder that work is, the longer they will stay on the old version (and keep asking us to support it). Users on old versions miss out on fixes and security patches, and in the meantime old and new versions of our library [collide in dependency graphs](/jbp/jlbp-21.html).

A migration guide is a good start, but it asks every user to apply the same changes by hand, one at a time, in every codebase they own. If a change can be described precisely enough to put in a migration guide, it can usually be described precisely enough to automate.

## Ship OpenRewrite recipes

[OpenRewrite](https://docs.openrewrite.org/) is an open source tool that refactors source code by applying *recipes*. It parses code into a type-aware tree, so its changes are accurate (it renames a method on *your* type, not every method with the same name) and it preserves the existing formatting. Users run recipes with a Maven or Gradle plugin, review the resulting changes, and commit them. Large-scale migrations - Java version upgrades, JUnit 4 to JUnit 5, `javax.*` to `jakarta.*`, and major Spring Boot upgrades - are routinely performed this way.

Many of the changes in a typical major release are covered by recipes that OpenRewrite already provides, and can simply be composed in a declarative YAML file:

```yaml
---
type: specs.openrewrite.org/v1beta/recipe
name: com.example.storage.MigrateToStorage3
displayName: Migrate to Example Storage 3.x
description: Migrates applications from Example Storage 2.x to 3.x.
recipeList:
  - org.openrewrite.java.ChangeMethodName:
      methodPattern: com.example.storage.BlobClient removeBlob(..)
      newMethodName: deleteBlob
  - org.openrewrite.java.ChangeType:
      oldFullyQualifiedTypeName: com.example.storage.BlobInfo
      newFullyQualifiedTypeName: com.example.storage.BlobProperties
  - org.openrewrite.java.ChangePackage:
      oldPackageName: com.example.storage
      newPackageName: com.example.storage3
      recursive: true
  - org.openrewrite.java.dependencies.ChangeDependency:
      oldGroupId: com.example
      oldArtifactId: storage
      newGroupId: com.example.storage3
      newArtifactId: storage
      newVersion: 3.0.x
```

More complex changes - reordering arguments, replacing one API pattern with another - can be written as imperative recipes in Java, or as before-and-after templates that OpenRewrite compiles into recipes. Recipes are tested with ordinary unit tests that assert the code before and after:

```java
class MigrateToStorage3Test implements RewriteTest {
    @Override
    public void defaults(RecipeSpec spec) {
        spec.recipeFromResources("com.example.storage.MigrateToStorage3")
            .parser(JavaParser.fromJavaVersion().classpath("storage"));
    }

    @Test
    void renamesRemoveBlob() {
        rewriteRun(java(
            """
            import com.example.storage.BlobClient;
            class A { void f(BlobClient c) { c.removeBlob("x"); } }
            """,
            """
            import com.example.storage3.BlobClient;
            class A { void f(BlobClient c) { c.deleteBlob("x"); } }
            """));
    }
}
```

Publish recipes as a separate artifact (for example, `com.example:storage-migration`) so they don't add to the library's own dependencies, and document the one command users need to run:

```shell
mvn -U org.openrewrite.maven:rewrite-maven-plugin:run \
  -Drewrite.recipeArtifactCoordinates=com.example:storage-migration:3.0.0 \
  -Drewrite.activeRecipes=com.example.storage.MigrateToStorage3
```

The core OpenRewrite framework is Apache-licensed, but some of the recipe modules published alongside it use other licenses - check the license of anything your recipes depend on.

## Automate smaller changes too

Migration tooling isn't only for major versions. When we [deprecate](/jbp/jlbp-14.html) an API in favour of a replacement that is a simple, mechanical substitution, we can annotate it with Error Prone's [`@InlineMe`](https://errorprone.info/docs/inlineme), which allows users running [Error Prone](https://errorprone.info/) to automatically replace calls to the deprecated API with its replacement:

```java
/** @deprecated Use {@link #deleteBlob(String)} instead. */
@Deprecated
@InlineMe(replacement = "this.deleteBlob(name)")
public void removeBlob(String name) {
    deleteBlob(name);
}
```

## Design the release with migration in mind

* Write the recipe *while* making the breaking changes, not after the release. If a change is hard to automate, that's a useful signal that it may be hard for users to understand too.
* Aim to automate the common cases, and document the rest. A recipe that handles 90% of the work, plus a short migration guide for the remainder, is far better than no recipe at all.
* Run the recipe against real code - your own samples, and some open source projects that use your library - before releasing it.
* Remember that much of the code being migrated is now written and maintained with the help of [AI coding agents](/jbp/jlbp-22.html). A deterministic, tested recipe gives an agent (and its human reviewer) a reliable way to perform the upgrade, rather than reconstructing it from release notes.
