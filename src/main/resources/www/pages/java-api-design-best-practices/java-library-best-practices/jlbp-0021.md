A *diamond dependency* occurs when an application depends on two libraries, `A` and `B`, which both depend on a third library, `C`. Drawn as a graph, it forms a diamond:

```
        app
       /   \
      A     B
       \   /
         C
```

This is completely normal, and is not a problem in itself. The problem arises when `A` and `B` depend on *different, incompatible* versions of `C`. Because both versions of `C` share the same coordinates, dependency managers such as Maven and Gradle resolve the conflict by selecting a single version to put on the classpath:

* **Maven** picks the version "nearest" to the application in the dependency tree, and if there is a tie, the one declared first. This is often *not* the newest version.
* **Gradle** picks the highest requested version (unless told otherwise).

Either way, at least one of `A` or `B` now runs against a version of `C` it was not compiled or tested against. If `C` made a binary-incompatible change between those versions, the application compiles successfully and then fails at runtime with a `NoSuchMethodError`, `NoClassDefFoundError`, `AbstractMethodError`, or `IncompatibleClassChangeError` - often only on a rarely-used code path, and often in production.

Nor is it safe to simply put both versions on the classpath. Nothing in the JVM stops you doing so, but the classpath is a flat list searched in order: a class loader typically loads the first matching class it finds, so `A` and `B` both end up with whichever copy of each class comes first - possibly a mixture of classes from both versions. The Java module system does not solve this either: a module configuration (and therefore a single module layer, such as the boot layer an application normally runs in) can only contain one module of a given name, so two versions of `C` cannot be resolved together there. Running them side by side requires separate class loaders or module layers, which is framework-level machinery, not something applications should need.

Application developers can only work around a diamond conflict (by excluding, overriding, or pinning versions, and hoping). It is *library* developers who cause them, and who are in the best position to prevent them. Each of us is `A`, `B`, or `C` in somebody's dependency graph.

## If you are `A` or `B`: depending on other libraries

* **[Minimize dependencies](/jbp/jbp-2.html).** Every dependency we take is a potential diamond for every user of our library. Prefer the JDK where it is now good enough (for example `java.net.http.HttpClient`), and consider whether [a little copying](/jbp/jbp-8.html) is better than a new dependency.
* **Choose dependencies with good compatibility track records.** Prefer libraries that follow [semantic versioning](/jbp/jlbp-5.html), that [resist breaking changes](/jbp/jlbp-6.html), and that rename their packages when they do break. Be wary of pre-1.0 libraries, and never use the internal (or `@Beta`, or `@Internal`) APIs of a dependency, as these can change in any release.
* **Don't expose dependencies in your public API.** If our public API exposes types from `C`, our users must use the same `C` we do, our major version becomes coupled to `C`'s major version, and we can never move to a new major version of `C` without breaking our own users. Keep dependencies [hidden](/jbp/jlbp-7.html) behind our own types.
* **Keep dependencies up to date.** Libraries that trail far behind the rest of the ecosystem are the most likely to end up on the losing side of conflict resolution. Regularly [updating dependencies](/jbp/jbp-4.html) keeps us close to what everyone else is using.
* **Make heavy integrations optional.** Rather than depending on a particular JSON or HTTP library, define a small interface and provide implementations in separate, optional modules, so users only pull in the dependencies they choose.
* **Test against the versions your users will actually get.** Run your tests with your dependencies resolved to their newest versions as well as the versions you declare, so you discover incompatibilities before your users do.
* **Treat [shading](/jbp/jlbp-10.html) as a last resort.** It does remove the conflict, but it comes with significant costs of its own.

## If you are `C`: being depended upon

The best thing a widely-used library can do for the ecosystem is to never make a binary-incompatible change without also making it *possible for the old and new versions to coexist*.

* **Don't break binary compatibility in minor or patch releases.** Use tooling such as japicmp or Revapi to enforce this, as discussed in [resist breaking changes](/jbp/jlbp-6.html).
* **When you must break, rename.** If a new major version changes both its Maven coordinates (`groupId` or `artifactId`) *and* its Java package names, then the old and new major versions are different libraries as far as both the build tool and the JVM are concerned. They can sit side by side on the same classpath, so `A` can upgrade to the new version while `B` stays on the old version, and the diamond disappears. This is how Apache Commons Lang 3 (`org.apache.commons.lang3`), Apache HttpClient 5 (`org.apache.hc.client5`), and Jackson 3 (`tools.jackson.*`) handled their major releases. Changing the package name without changing the coordinates (or vice versa) does not work - you need both.
* **Keep the old major version alive for a while.** Even with renamed packages, the ecosystem takes time to migrate. Continue shipping security fixes for the previous major version, as described in your [deprecation policy](/jbp/jlbp-14.html).

## If you publish many libraries: align them

When a project ships many libraries (for example, an SDK with one library per service), its libraries depend on one another and on the same third-party libraries, and are therefore the most likely source of diamonds in their users' applications. Build all of them against the same versions of shared dependencies, release them regularly, and [publish a BOM](/jbp/jlbp-4.html) whose transitive closure has been verified to converge.

## Detecting diamond conflicts

Conflicts are far cheaper to fix when they are detected at build time:

* The Maven [Enforcer plugin](https://maven.apache.org/enforcer/enforcer-rules/index.html) provides `dependencyConvergence` (fail if the graph contains more than one version of any dependency) and `requireUpperBoundDeps` (fail if the resolved version is lower than one that some dependency asked for).
* In Gradle, `resolutionStrategy.failOnVersionConflict()` fails the build on any version conflict, and `./gradlew dependencyInsight --dependency <name>` explains how a version was chosen.
* `mvn dependency:tree -Dverbose` shows which versions were omitted due to conflicts.
* Google's [Linkage Checker](https://github.com/GoogleCloudPlatform/cloud-opensource-java/tree/main/linkage-checker) inspects the resolved classpath and reports references to classes and methods that do not exist - finding the actual runtime errors, not just the version disagreements.
