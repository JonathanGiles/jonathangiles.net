Very rarely these days does software get developed by a single person, and even if it did, the human condition is so fickle that what they deem is great one day may be considered dead wrong the next (trust me, I've seen far too many conversations where somebody asks "why are you doing it this way" in consternation and disgust, only to be told it was them). Fortunately, as we design API, we have a clear record of the decisions we have made in the form of our public API, and it can be quite easy to spot when something is deviating from this forming convention.

The short term benefit to having consistent API is that we reduce the risk of frustrating our users, and the long term benefit is that a consistent API ensures that when an end user arrives at a new section of your API, that they are more readily able to intuit how it should be used.

The single most effective thing a team can do here is to *write down* its conventions. Microsoft publishes the [Azure SDK design guidelines](https://azure.github.io/azure-sdk/java_introduction.html) that every Azure SDK for Java library must follow, and these are enforced through a combination of API review and automated tooling (such as custom CheckStyle rules). Your guidelines don't need to be anywhere near as extensive, but even a single page covering naming, nullness, exceptions, and collections goes a long way. Pair this with a lightweight API review process, where a small group with a broad view of the API reviews each new public API before it ships.

Some of the more important considerations around consistency are covered in the remainder of this best practice.

### Return types

Ideally all API that must return a collection should be consistent, using only a few classes rather than all possible ones. A good subset of collections to return might be, for example, `List`, `Set`, and `Iterator` (and in this case, never `Collection`, `Iterable`, and `Stream` - but note that these are all valid return types - just in this example they were chosen to not be in the subset). Relatedly, if the API takes pains to not return null in most cases (for a certain return type), it is best advised to never return null for that return type. See [don't return null](/jbp/jlbp-15.html) and [make nullness explicit](/jbp/jlbp-18.html).

### Method naming patterns

Developers rely on their IDE to auto-complete their input, so consider the importance of API naming, to ensure related concepts appear adjacent to each other in the user's auto-complete popup lists. An API should have a well established set of terms and reuse those terms all the time in: type names, method names, argument names, constants, etc. Method names like `Type.of(...)`, `Type.valueOf()`, `Type.toXYZ()`, `Type.from(...)`, etc. should be used consistently, and never mixed. Our goal is to have a team-wide vocabulary that we use throughout our API. For example, if one client has a `deleteBlob` method, another client should not have a `removeQueue` method.

The same applies to accessor style. Decide whether your API uses JavaBean-style `getName()` / `setName(...)` accessors, or record-style `name()` accessors, and apply it consistently - mixing the two within a single API is jarring.

### Argument order

APIs that overload methods to accept different numbers or types of arguments should always ensure that the ordering is consistent and logical. In some cases the arguments we pass into a method form some logical grouping, and in these cases it may make sense to introduce an intermediate argument type that can wrap these arguments. This reduces the risk that subsequent releases of our API will need to overload the method to accept more arguments. This also helps to aid our goal of API evolvability.

### Exceptions

Decide up front how your API reports errors, and apply that decision everywhere. Will you use checked or unchecked exceptions? (Most modern Java APIs favour unchecked exceptions.) Will you have a common base exception type for your library, so users can catch all of your errors in one place? What information will every exception carry (an error code, the HTTP status, a request ID)? Users who learn how to handle errors from one part of your API should be able to apply that knowledge everywhere else.

### Construction patterns

Users should be able to guess how to create an instance of any type in your API. If most of your client types are created via a builder (e.g. `new FooClientBuilder().endpoint(...).buildClient()`), then *all* of them should be. Similarly, decide whether you use public constructors, static factory methods (and what you name them - `of`, `from`, `create`, `newInstance`), or builders, and use each in a consistent, predictable set of circumstances.

### Sync and async

If your API offers both synchronous and asynchronous variants, make them mirror each other. Ideally, every operation available on the sync API is available on the async API, with the same name, the same parameters, and the async variant differing only in its return type (for example, returning a `CompletableFuture<T>` or a reactive type rather than `T`). With virtual threads now available in Java 21 and later, it is worth questioning whether a separate async API is needed at all, as simple blocking APIs now scale far better than they once did (see [be virtual thread friendly](/jbp/jlbp-23.html)).

### Nullness and optionality

Apply a single policy for nullness across your API - for example, "parameters and return values are non-null unless annotated otherwise". Ideally this policy is captured in code, using [JSpecify annotations](/jbp/jlbp-18.html), so that it can be checked by tools rather than just documented.

### Automate what you can

Consistency is far easier to maintain when it is enforced by tools rather than by memory. Custom CheckStyle rules, Error Prone checks, ArchUnit tests, and [API compatibility tooling](/jbp/jlbp-6.html) can all be used to catch inconsistencies before they ship. Anything that cannot be automated should be on the checklist for API review.
