In [don't return null](/jbp/jlbp-15.html), we discussed strategies for avoiding `null` return values. But no matter how careful we are, `null` remains a part of Java, and our users need to know, for every parameter and return value in our API, whether `null` is allowed. Historically, the only way to communicate this was in JavaDoc ("must not be null", "may return null"), which is easy to forget to write, easy to forget to read, and impossible for tools to verify.

For many years, the Java ecosystem tried to solve this with annotations, but ended up with a fragmented mess: JSR 305's `javax.annotation.Nonnull` (from a JSR that was never completed, and which causes split-package problems on the module path), plus competing `@Nullable` annotations from JetBrains, the Checker Framework, Android, Eclipse, Spring, and others, each with subtly different semantics. Library developers had to pick one, and tools had to understand them all.

## JSpecify

[JSpecify](https://jspecify.dev/) is the answer to this fragmentation. It is a collaboration between many of the organizations that previously had their own annotations (including Google, JetBrains, Meta, Oracle, Uber, the Spring team, and others), and it released version 1.0 in 2024. It provides a small set of annotations with precisely-specified semantics, in a tiny dependency with no transitive dependencies of its own, and with a proper `module-info`. It has rapidly gained adoption, including throughout Spring Framework 7 and Spring Boot 4.

The key annotations are:

* **`@NullMarked`**: applied to a package (in `package-info.java`), module, or class. Within this scope, all types are considered non-null *unless* annotated otherwise.
* **`@Nullable`**: indicates that `null` is an acceptable value for this type usage.
* **`@NonNull`**: rarely needed inside `@NullMarked` code, but useful in unmarked code or for specific generic cases.
* **`@NullUnmarked`**: opts a scope back out of `@NullMarked`, which is helpful when migrating an existing codebase incrementally.

## How to apply it

Because the overwhelming majority of parameters and return values in a well-designed API should be non-null, the most effective approach is to mark entire packages as non-null by default, and then annotate only the exceptions. Add the dependency:

```xml
<dependency>
  <groupId>org.jspecify</groupId>
  <artifactId>jspecify</artifactId>
  <version>1.0.1</version>
</dependency>
```

Mark each package as null-marked in its `package-info.java`:

```java
@NullMarked
package com.example.cars;

import org.jspecify.annotations.NullMarked;
```

Then annotate only the places where `null` is genuinely allowed:

```java
public final class Garage {
    // Non-null parameter, non-null return value
    public List<Car> findCars(String owner) { ... }

    // Returns null if no car is parked in the given bay
    public @Nullable Car carInBay(int bay) { ... }

    // The nickname is optional
    public void park(Car car, @Nullable String nickname) { ... }
}
```

Note that JSpecify annotations are *type-use* annotations, which means they are written immediately before the type they apply to. For arrays and nested types this matters: `@Nullable String[]` is an array of nullable strings, whereas `String @Nullable []` is a nullable array of strings.

In terms of scope, JSpecify is a compile-time-only concern for our users, but the annotations do need to be available on the classpath when our library is compiled against by tools that read them. It is therefore generally recommended to use a normal (compile) scope dependency, rather than `provided` / `compileOnly`, and since the JAR is tiny with no dependencies of its own, this costs our users essentially nothing. If you ship a `module-info.java`, use `requires static transitive org.jspecify;`.

## Checking nullness in the build

Annotations by themselves are documentation that IDEs (such as IntelliJ IDEA) understand and use to warn developers as they type. The real value comes when they are *verified*. [NullAway](https://github.com/uber/NullAway), which runs as an [Error Prone](https://errorprone.info/) plugin (see [configure build plugins](/jbp/jbp-6.html)), is fast enough to run on every compile and can fail the build when our code violates its own nullness contracts - for example, by returning a possibly-null value from a method that is not annotated `@Nullable`. The [Checker Framework](https://checkerframework.org/) offers a more thorough (but slower) alternative.

## Benefits for users of other languages

Explicit nullness annotations are also a significant improvement for users calling our library from Kotlin. Kotlin understands JSpecify annotations and maps them to its own nullable (`String?`) and non-null (`String`) types, rather than treating every value from Java as a *platform type* of unknown nullness.

## Adding annotations is an API change

Finally, be aware that nullness annotations are part of our public API contract. Changing a parameter from `@Nullable` to non-null, or a return value from non-null to `@Nullable`, can break users (particularly Kotlin users, where it becomes a compile error). Treat these changes with the same care as any other [potentially breaking change](/jbp/jlbp-6.html). When first annotating an existing library, take care to get the annotations right, and consider calling out the change in release notes.
