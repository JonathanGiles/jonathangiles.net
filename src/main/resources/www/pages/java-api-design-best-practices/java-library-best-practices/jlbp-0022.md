A growing share of the code that calls our libraries is no longer typed by a human. It is written by AI coding assistants and agents, with a human reviewing (or sometimes not reviewing) the result. This changes who our "users" are. An agent has read a lot of code, but its knowledge was frozen at some point in the past, it is heavily biased towards whatever was most common in its training data (which is usually an *older* version of our library), and it will confidently invent methods that do not exist.

The good news is that almost everything that helps an agent use our library correctly also helps humans. The difference is one of degree: humans tolerate an inconsistent API or a vague error message, and eventually work it out. Agents produce wrong code, quickly and at scale. The practices below are about making the right code the *likely* code.

## Make the API guessable

Agents work largely by predicting what an API *probably* looks like. The more [consistent](/jbp/jlbp-12.html) and conventional our API is, the more often those predictions will be correct.

* Use the same verbs, nouns, construction patterns and accessor styles everywhere. If one client has `deleteBlob`, an agent will assume another has `deleteQueue` - make sure it does.
* Follow the conventions of the JDK and the wider ecosystem rather than inventing our own. `of`, `from`, `builder()`, `close()` and `AutoCloseable` are what an agent will reach for first.
* Prefer strong types to strings: enums, value types, and builders turn an agent's mistakes into compile errors, which agents are very good at reacting to. [Explicit nullness](/jbp/jlbp-18.html) annotations do the same for null handling.

## Remember that old versions live forever in training data

Agents will keep generating code against the API of an old version of our library long after we have moved on. We can't prevent this, but we can make it cheap to recover from:

* [Resist breaking changes](/jbp/jlbp-6.html). Every rename turns a large body of training data into wrong answers.
* When we do replace an API, prefer [deprecating](/jbp/jlbp-14.html) the old one over removing it, and make the `@deprecated` Javadoc state exactly what to use instead. Agents read compiler warnings and Javadoc, and will follow a clear instruction.
* Ship automated migrations. [OpenRewrite](https://docs.openrewrite.org/) recipes give agents (and humans) a deterministic way to upgrade code from one major version to the next, rather than relying on the agent to work out the migration from release notes.

## Make documentation available to tools

Agents increasingly read documentation at the moment they write code, rather than relying only on what they remember. We should make that easy:

* Always publish sources and Javadoc JARs to [Maven Central](/jbp/jlbp-3.html) - IDE-integrated agents use these to look up the real signatures of the version on the classpath.
* Write [great Javadoc](/jbp/jlbp-11.html) with complete, compilable examples (the `{@snippet}` tag, available since Java 18, allows examples to be validated against real source code). Agents copy examples far more faithfully than they follow prose.
* Keep runnable samples in the repository, and build and test them in CI, so they never go stale.
* Clearly version the documentation, so that it is obvious which version of the library a page applies to.
* Consider publishing documentation in a form that is easy for tools to consume, such as Markdown versions of each page, or an [`llms.txt`](https://llmstxt.org/) index at the root of the documentation site.

## Write error messages for the next attempt

An agent's workflow is a loop: write code, run it, read the error, try again. The quality of our exception messages largely determines how many iterations that loop takes - and whether it converges at all.

* Validate arguments eagerly and fail fast, at the point of the mistake rather than deep inside the library.
* Say what was wrong, what was expected, and how to fix it. `"endpoint must be an absolute https URL, but was 'storage.example.com'. Did you mean 'https://storage.example.com'?"` is far more useful than `"Invalid endpoint"`.
* Include stable error codes and links to documentation where appropriate.

## Ship guidance for agents

Most coding agents can be given additional, project-specific instructions. Library authors can take advantage of this:

* Add an `AGENTS.md` file to the repository describing how to build, test, and contribute to the library, so agents working *on* our library follow our conventions.
* Consider publishing guidance for agents that *use* our library - for example, an agent skill (a `SKILL.md` file containing instructions and examples) that describes how to set up the library, its idiomatic usage, its common pitfalls, and how to migrate from older versions.
* If our library is the client for a service, consider also providing a [Model Context Protocol](https://modelcontextprotocol.io/) (MCP) server, so agents can look up documentation or interact with the service directly.

## Protect your users from hallucinated dependencies

Agents sometimes invent plausible-sounding dependency coordinates that don't exist, and attackers have begun registering such names to distribute malware (a technique known as *slopsquatting*). Use a single, consistent `groupId` that we verifiably own, document the exact coordinates (and the [BOM](/jbp/jlbp-4.html)) prominently, and consider claiming obvious variations of our project's name. Users should also follow the advice in [secure your software supply chain](/jbp/jbp-9.html).
