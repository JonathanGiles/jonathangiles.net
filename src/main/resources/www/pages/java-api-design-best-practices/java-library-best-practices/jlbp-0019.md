Many of the types in a typical API are simple carriers of data: a `Point`, a `Money` amount, a `BlobProperties` result returned from a service call. Making these types *immutable* - so that their state can never change after construction - is one of the simplest ways to make an API safer and easier to use. As Joshua Bloch puts it in *Effective Java*: "classes should be immutable unless there's a very good reason to make them mutable."

Immutable types have a number of advantages:

* **They are inherently thread-safe.** They can be freely shared between threads without synchronization, which matters more than ever in a world of virtual threads and highly concurrent applications.
* **They are easy to reason about.** A value that cannot change cannot be put into an inconsistent or illegal state by a user (or by our own code) - a problem we discussed in [minimize API visibility](/jbp/jlbp-7.html).
* **They can be safely cached, shared, and used as keys** in `HashMap` and `HashSet`, without the risk of their hash code changing.
* **No defensive copying is required** when they are passed into or returned from our API.

## Records

Java 16 introduced [records](https://openjdk.org/jeps/395), which make defining an immutable data carrier extremely concise:

```java
public record Point(int x, int y) {
    public Point {
        if (x < 0 || y < 0) {
            throw new IllegalArgumentException("Coordinates must be non-negative");
        }
    }
}
```

From this single declaration, the compiler generates a `final` class with `private final` fields, a canonical constructor, accessor methods (`x()` and `y()`), and `equals`, `hashCode`, and `toString` implementations. The *compact constructor* shown above allows validation (and normalization) of the inputs. Records also work with record patterns (Java 21), allowing users to destructure them in `instanceof` and `switch`:

```java
if (shape instanceof Point(int x, int y)) { ... }
```

## Records in public API: think about evolution

Records are excellent, but before exposing a record in a library's public API, we must understand what we are committing to. A record's API is *derived from its components*: the canonical constructor's parameter list, the accessor methods, and the semantics of `equals`, `hashCode`, `toString`, and deconstruction patterns are all determined by its component list. That means:

* **Adding a component is a breaking change.** It changes the canonical constructor's signature, which breaks every user who constructs the record. (We can mitigate this by adding a secondary constructor with the old signature, but user code that deconstructs the record with a record pattern will still break.)
* **Removing, renaming, or reordering components is a breaking change**, for the same reasons.
* **The internal representation is the API.** We cannot later change how the data is stored without changing the public API.

The guidance is therefore to use records in public API for small, stable value types whose components are inherent to what the type *is* - a `Point` will always have an `x` and a `y`. For types whose set of properties is likely to grow over time (such as model types representing a web service response, or [options types](/jbp/jlbp-9.html)), a regular `final` class with private fields and accessor methods (and perhaps a builder) gives us far more room to [evolve without breaking](/jbp/jlbp-6.html).

Records are, of course, perfectly suited for use *inside* our implementation, where these evolution concerns don't apply.

## Immutable classes

When a record isn't appropriate, we can still make a class immutable by following a few rules:

1. Make the class `final` (or use a private constructor with static factory methods), so subclasses cannot add mutable state.
2. Make all fields `private` and `final`.
3. Don't provide any methods that modify state. Where a 'modification' is needed, return a new instance instead (e.g. `withX(int x)`), as the `java.time` API does.
4. Ensure exclusive access to any mutable components. If a field refers to a mutable object (such as a `List` or an array), make a defensive copy on the way in, and never return the internal reference. For collections, `List.copyOf(...)` (Java 10) is ideal, as it produces an unmodifiable copy (and avoids copying if the input is already an unmodifiable list).

```java
public final class Playlist {
    private final String name;
    private final List<Song> songs;

    public Playlist(String name, List<Song> songs) {
        this.name = Objects.requireNonNull(name);
        this.songs = List.copyOf(songs);
    }

    public String getName() { return name; }

    // Safe to return directly, as the list is unmodifiable
    public List<Song> getSongs() { return songs; }

    public Playlist withSong(Song song) {
        List<Song> newSongs = new ArrayList<>(songs);
        newSongs.add(song);
        return new Playlist(name, newSongs);
    }
}
```

The same rule about mutable components applies to records: a record with a `List` component is only shallowly immutable unless the compact constructor makes a defensive copy (`songs = List.copyOf(songs);`).

## When mutability is appropriate

Immutability is a default, not an absolute. Builders and [options types](/jbp/jlbp-9.html) are intentionally mutable, as are types that model inherently stateful things (connections, clients, caches). The goal is simply to make mutability a deliberate decision, rather than an accident of habit.
